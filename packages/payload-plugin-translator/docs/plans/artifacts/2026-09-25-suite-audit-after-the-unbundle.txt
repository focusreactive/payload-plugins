Suite audit — does anything hold the behaviour after the request-scope unbundle?
================================================================================
Target: the uncommitted unbundle (`git diff ed3460cc`, 26 files, +303/-182). The slice was split
into three files, two single-consumer files moved to their consumer, and the half-identity
(`userId?` + `userCollection?`) collapsed into one `requester?: Requester | null`.

Method: audit mode. A red config aliased each of the three units to a throwing stub — whatever stays
green on a stub is proven worthless. Then four mutations against the real code. Every integration
mutation rebuilt `dist` first, because apps/dev resolves the plugin from there.

Part 2 — four mutations
-----------------------
1. requesterOf:  `id == null || collection == null`  ->  `!id || !collection`

   `requesterOf` is the single place that turns the two stored columns back into an identity, and

2. identityOf:  `user.id == null`  ->  `!user.id`

   The zero-id risk IS still held here. The claim in the contract's review log is correct about the

       killedTheCallersTransaction.test.ts    1 failed / 5

4. the unattributed bypass:  `if (!requester) return ALLOW_ALL`  ->  never taken
       unit    3 files failed / 131

   "A scope naming nobody skips the permission check" — the security-relevant behaviour the deleted

Finding: the deletion was sound, the refactor added the gap
-----------------------------------------------------------
The contract argued that removing `describe("isAttributed")` (6 checks) lost nothing, because five
of its cases became unrepresentable and the sixth (zero id) lives on in identityOf.test.ts.
Mutations 2 and 4 confirm that argument.

But D5 created a SECOND place that makes the same decision from the same raw material — a possibly
zero id and a possibly empty collection — and only the first one is guarded. The old code decided
"is this an identity?" once, in `isAttributed`, and that one predicate was tested. The new code
decides it in `identityOf` (tested) and again in `requesterOf` (untested). Collapsing the type
removed the need for a guard at every *reader*; it did not remove the need for one at every
*producer*, and the audit found the producer nobody checks.


Also found
----------
`server/shared/payload/index.ts` is imported by nobody — 0 hits across the package and apps/dev.
Every other `shared/*` subdirectory's barrel is re-exported from `server/shared/index.ts`; this one
is not. As it stands it is a file that exists to look tidy.

Second pass — 2026-09-30, over the ten files changed after the first audit
================================================================================
The first audit above covered the unbundle up to `asRequester`. Three further rounds of work
followed, none of which it had seen: the round-trip export (the deep review's finding 3), the public
type export (its finding 2), and three "contract instead of comment" rewrites. This pass audits only

Why it was needed, stated plainly: the three rewrites were shipped on a green suite and reported as
done. When the owner asked whether anything actually tested them, two of the three turned out to be
guarded by nothing — mutating them left all 132 files green. The tests below were written after that
question, and this pass re-proves them rather than trusting the author's own run.

Finding — the public export is held by nothing
-----------------------------------------------
    removing `export type { RequestScope, Requester }` from src/index.ts
        unit          1605 passed / 1605     NOTHING RED
        check-types   clean                  NOTHING RED

This export exists precisely because a third-party `TaskRunnerProvider` must name the type it is
handed. Nothing states that, so it can be deleted silently by anyone tidying the barrel — and the
consumer it exists for lives outside this repository, where the breakage surfaces.

The package has no public-surface test of any kind, so this is a convention that does not exist yet
rather than one that was skipped.


Finding — the package's own `@since` rule is half-applied
----------------------------------------------------------
`packages/payload-plugin-translator/CLAUDE.md` requires two things for anything re-exported from
`src/index.ts`: `@since x.y.z` in the JSDoc, *and* a `Since vX.Y.Z` note in README.md beside the
feature. The JSDoc carries `@since 0.14.0`; README.md does not mention 0.14.0 at all.


Correction to the record — one justification in this work was false
--------------------------------------------------------------------
The `SyncTaskRunner` rewrite replaced a comment claiming "`finally`, not after the `try`: the rethrow
must still leave a timestamp, or `LazyMap` never evicts the failed task." That is wrong. `LazyMap`
evicts on `isRemovable`, which reads `status`; `updatedAt` only orders the queue, so a stale stamp
would evict *sooner*, never "not at all".

Checked again this pass, and the second story needed narrowing too: `updatedAt` does break a tie in
`get-document-status/model.ts:62-65`, but that tie is unreachable for the sync runner, whose map key
already includes the locale — one task per locale, nothing to tie-break. What is real and reachable
is that `updatedAt` is returned to the panel as `updated_at`, so a settled task reporting its start
time is wrong information on screen. The checks assert that, and mutation 4 proves they do.

was created — audit mode needs none, the mutations are the instrument. Files restored from copies,
never `git checkout --`, because the tree carries other sessions' uncommitted work.
