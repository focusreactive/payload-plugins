# Does #177 earn its four `Closes` keywords?

Research, 2026-10-12. Read-only: no code touched, no issue changed, no commit made.

## The question

PR #177 carries `Closes #107, closes #110, closes #106, closes #103`, so merging it closes all four
automatically. Before that happens: is each of them genuinely answered, deliberately declined, or
quietly skipped?

Verdicts use three values only — **closed** (the need is met), **declined on the record** (not met,
and the decision is written down with its alternative), **skipped** (not met and nowhere mentioned).

## Issue by issue

### #107 — "enqueue should return the job ids it created" → **closed**

The answer now carries one entry per requested locale, each naming the run:

```
assignments: [{ collection_slug, collection_id, target_lng, handle }]
```

The issue's *suggested shape* was a locale-keyed map, `jobs: { fr: "…", de: "…" }`. That was
rejected on the record and the rejection holds up: the request accepts an **array** of documents
(`enqueue-translation/model.ts:15`, `collection_id: z.array(...).nonempty()`), so a map keyed by
locale collapses several documents onto one key. The flat list answers the stated need — "the ids
exist at that point; they are just not returned" — and names the document as well, which the map
could not.

Proof: `apps/dev/src/integration/translator/enqueue-handles.int.test.ts`, which asserts one answer
per requested locale naming a run that really exists.

### #103 — "collection status should return document id and target locale" → **closed**

`get-collection-status/handler.ts:45` now maps each task to
`{ id, status, collection_id, target_lng }`, pinned by `handler.test.ts:144–146` with three entries
across two documents.

The issue wrote `collectionId` / `targetLng` because it was naming the internal `Task`'s fields. The
wire format of this plugin is snake_case throughout — the same endpoint family takes `source_lng`,
`target_lng`, `collection_slug` on the way in — so the delivered names are consistency with the
surface the issue is about, not a substitution. The issue's own framing, "a response-mapping change,
not new plumbing", is exactly what happened.

### #110 — "pass run context into lifecycle callbacks" → **two parts declined on the record, the need met; one part narrowed**

Three distinct asks, and they ended differently.

**The opaque `context` → declined, by the issue's own alternative.** The plugin does not accept a
host value and hand it back. It generates a run handle instead and puts it on every callback,
`onQueued` included. The issue offers this itself: *"A run id generated by the plugin and passed to
callbacks would also solve it."* Recorded as D1 with the rejected alternative.

**The attempt counter → declined by name, and the need behind it met another way.** The contract
says so plainly: *"Rejected: an `attempt` counter, which is what #110 asks for by name. It lets a
host tell the events apart but still cannot say whether another try is coming, so it does not let
them turn retries back on — it answers the request, not the need."* The need was "must run with
`retries: { attempts: 0 }`". `onFailed` now fires once, and only when the locale will not be
translated — so retries can be switched back on. Proof:
`final-failure.int.test.ts:63`, "says nothing while the run is still retrying, and reports success
once it works".

**"Removes the need for the single-open-run constraint" → narrowed, not erased, and recorded.** The
host no longer has to enforce that constraint to make its join unambiguous — the handle does that.
But the plugin still coalesces: a second request for a locale a live run already covers joins that
run and is answered with its handle (`model/alreadyCovered.ts`). So the issue's specific complaint —
*"a host cannot run two translations of the same pair concurrently even where that would be
harmless"* — still stands. This is D8, in the contract's own words: *"Semantically right — there was
one translation — but it means #110 is narrowed rather than erased, and the README should say so."*

### #106 — "an onCancelled lifecycle callback" → **closed, and one of its two requirements has expired**

`onCancelled(task)` exists (`lifecycle/types.ts:69`), fires once per locale the run still owed, and
fires **before** the row is deleted — which is what the issue asked for so a host can still read the
row.

The `reason` argument was not delivered. That is not a gap: the issue names two paths, and the
second one no longer exists. Verified independently rather than taken from the contract —
`__tests__/PayloadJobsTaskRunner.test.ts:241`, "never cancels or deletes a job when enqueuing", is a
regression test asserting the plugin's own supersede path is gone. With explicit cancellation the
only path left, `reason` would carry one value.

So the issue's premise *"the plugin cancels jobs on its own initiative and tells nobody"* is stale
relative to the branch, and saying `reason` is missing would be scoring the letter over the fact.

## Is any of the four skipped?

**No.** Every requirement is either met, or declined with its reason and its rejected alternative
recorded in `2026-10-06-lifecycle-run-context.task.md` under `## Decisions by the owner`.

## The one thing that should block a clean conscience at merge

**The README still documents the old behaviour, and it is the document a consumer reads.**

`README.md:419` says today:

> `onQueued` fires once; `onCompleted` / `onFailed` fire per execution attempt, so a retried task can
> emit `onFailed` more than once.

That is precisely what #110 complained about and what this PR changed. The code says the opposite
(`lifecycle/types.ts:37`, "Each fires once per target locale, never per attempt"). The README also
does not mention the handle on `TranslationTask`, nor `onCancelled`, nor the coalescing that D8 says
it should state.

So: the four issues are answered in the code and contradicted in the docs. A consumer who reads the
README after this merges would still believe they must run with retries disabled — the exact
condition #110 was filed to lift.

`README.md` is the owner's to edit by standing agreement, which is why it is reported rather than
changed. It is the only outstanding item this research found.

## Open questions

   attempt counter?** Matters because: if they wanted per-attempt visibility for a progress display

   already carries this as a handoff item, never scored.
2. **[non-blocking] Is the coalescing in D8 acceptable to them?** Matters because: #110's text calls
   the single-open-run constraint "a real constraint we would rather not need". It is still there,
   imposed by the plugin instead of by them.

Both are questions for the consumer, not for the code, and neither changes a verdict above.
