# The swap

Build step: 2026-11-06-the-swap.design.md #3

Two walkers coexist. The pipeline's own — `FieldChunkCollector` plus `stages/text-expander/` — is
the one in use; the traversal engine with its two languages is written, tested and wired to
nothing. This step retires the first, and with it the defect the epic was opened for: text inside a
block embedded in a rich text is never translated, because the old walker treats such a field as
one leaf and never looks inside it.

## Requirements

- R1 (in) The pipeline translates through the walk, and `FieldChunkCollector` and
  `stages/text-expander/` are deleted.
- R2 (in) A run's fingerprints are computed by the same walk, with the same languages and the same
  block list, as the translation.
- R3 (in) All three joints — what may be translated, what counts as changed, what the receipt
  records — speak one address vocabulary, folded to field level.
- R4 (in) For a rich text with no embedded block, the hashed text equals the old projector's string
  exactly, so such a document does not go stale. Held by construction — see below.
- R5 (in) An answer whose shape does not match its target is reported, not dropped in silence.
- R6 (out) Finer-than-field receipt addresses. Deferred by D1, and its own body of work.

## Why it cannot be staged

Three things read addresses from one function, `projectTranslatableContent`: selection
(`everyTranslatableLeaf`), staleness (`computeFieldFingerprints`) and the receipt
(`ProvenanceService.record`). The recorder matches by string equality —
`sent.get(address)` against the fingerprint map's keys.

Move the translation side alone and `sent.get("body")` is `undefined` for every document, forever.
`claimToRecord` then writes `UNANSWERED`, which reads as changed, so the next run selects the field,
translates it, fails to record it, and marks it stale again. No number of runs settles it.

Move the fingerprint side alone and the mirror opens: recording claims the embedded text was
translated when it was not, and because the hash then matches, nothing ever notices.

## Decisions

### D1. The languages are passed into the pipeline, not imported by it

`src/core` may not import `src/languages` — pinned by a scan that allows a type-only reach from a
test fixture and nothing else. The walk needs both languages, so something must bridge them.

Chosen: `translateContent` takes `languages: readonly RegisteredLanguage[]`, a type that already
belongs to `core/traversal`, and the server layer constructs `payloadFieldsLanguage(...)` and
`payloadLexicalLanguage()` and passes them. Core never names a language; it receives them.

- *Rejected — invert the pipeline, so the caller runs the walk and hands over the targets.* It
  moves the provider protocol, the failure codes and the settling out of `core` with it, for a
  boundary that a parameter already satisfies.
- *Rejected — move the pipeline out of `core`.* The same, larger.

### D2. The walk records the address each target folds onto

D1 of the design says the fold point exists in the engine — at the moment `boundary` returns a
crossing, that `idPath` is the field's address. It exists but is not kept: a target carries only
its own `idPath`, and from `["body", "i1:mention", "label"]` nothing says where the field ended and
the embedded content began.

Chosen: the walk carries the address of the **first** crossing taken from the entry down each path,
and a target records it. A target reached without crossing folds onto its own address.

- *Rejected — fold by comparing prefixes against the schema's field addresses.* It reconstructs
  outside the walk what the walk knew and discarded, and it guesses wrong for a field whose own
  address is a prefix of another's.
- *Rejected — make the receipt per-target.* That is R6, deferred by the design's D1.

### D3. One function answers all three joints

`projectTranslatableContent` is replaced, for the three joints, by one walk-backed function
returning per folded address: the text under it, and the targets beneath it. Selection reads its
addresses, staleness hashes its text, the pipeline translates its targets.

The old projector stays only where it is not about a run — `computeSourceFingerprint`, which gates
automatic translation on save and compares a document against itself, is explicitly **not** the
receipt (design D9) and does not need the walk.

### D4. The two kernel fixtures that amend the target tree are brought in line here

`fixtures/payloadFields.ts` and `fixtures/storyblok.ts` hand over the target tree at a rich-text
boundary, against the owner's decision of 2026-11-08 that the source always replaces the target in
full. They are the kernel's coverage of a second and third host, and this step is where write-back
is decided, so leaving them would mean the kernel asserts behaviour the contract forbids while the
swap lands.

## The promise that does not hold

R4 is the reason the design could decide against a receipt migration: if a document without an
embedded block hashes exactly as before, it does not go stale, and no migration has to exist.

**Measured, not argued — it is false.** A rich text holding a blank text node between two
non-blank ones:

```
input   paragraph: "Hello" · " " · "world"
old     "Helloworld"     ← leafSourceText drops blank nodes
fold    "Hello world"    ← the fragment collector glues a blank onto the piece before it
```

The two were always going to disagree here: the rich-text language's own comment says the two cuts
disagree on whitespace nodes, and that is why the per-node fallback exists. What was missed is that
the **hash** inherits the disagreement, not only the cut.

It matters because Lexical splits a run wherever formatting changes, so a space landing in its own
node is ordinary rather than exotic. The set of documents that would be marked stale once is
therefore much wider than D9 costed: not "documents holding a block inside a rich text" but those
plus every document whose rich text has a blank node between two runs.

**Resolved 2026-11-09, by measurement rather than argument.** Two ways were tried against the real
projector before either was designed in.

*Tried and refused — drop the blank pieces before joining.* It cannot work: the fragment collector
glues a blank node onto the text of the piece **before** it, so there is no blank piece to drop.
Measured on six documents; it still differed on two.

*Chosen — the hash is a sum, not a re-derivation.*

```
hash(field) = what the old projector already produces for it
            + the text of everything found below a crossing at that field
```

The first term is the existing code, unchanged and uncalled-for-review, so a field with no embedded
block provably cannot move — not "should not", cannot, because nothing about its computation
changed. The second term is only ever content the old engine never reached, which is the whole
point of the epic. Measured on the same six documents plus a block case: prose-only reproduces the
old string byte for byte, and a field holding a block yields exactly the old string plus the block's
text.

This also removes a coupling an audit had flagged as a risk: the receipt's hash is no longer a
function of how a language chooses to cut text.

**One key set does move, and it is intended.** A rich text whose only text sits inside an embedded
block has no entry at all today — its own prose is empty — and gains one. That is the D9 staleness,
and it is now exactly one document shape rather than an unknown fraction. A rich text holding only
whitespace gains nothing, in either path.

## A correction to the premise, found while building

The section above names three joints. There are **four production call sites**, and two of them
cannot take the route D1 describes:

| Site | Part of a run? | Can be handed the languages? |
|---|---|---|
| `selectLeaves.ts:52` — selection for a document run | yes | yes |
| `translate-field/handler.ts:145` — selection for a single-field run | yes | yes |
| `Provenance.service.ts:95` — the fingerprint a run captures | yes | yes |
| `Provenance.service.ts:275` — `sourceAsItStands`, serving the admin panel's staleness and the accept button | **no** | **no** |

The fourth has no run behind it and therefore no `languages` and no block list. If it keeps reading
the old projector while the first three move to the fold, then for a document holding a block
inside a rich text the panel and the receipt disagree permanently: the panel hashes the prose only,
the receipt hashes prose plus block, and the document reads stale for ever.

So the swap owes an answer here, and AC3 as written compares one pair rather than all four. Either
the fourth site is given the same languages the plugin already resolves at boot — the embed table
step 1 put on the run's dependencies is reachable from the plugin config, not only from a run — or
staleness for the panel is defined to be the run's recorded hash rather than a recomputation.

**Decided — the fourth site is given the same walk.** The embed table the plugin resolves at boot
is reachable from the plugin config, so `ProvenanceService` is constructed with it and both of its
hashing sites go through one method. The panel therefore keeps measuring what it measured — the
source document — and measures it the way the receipt does. The alternative, defining the panel's
staleness as the run's recorded hash, was rejected: it would stop reporting edits made since the
last run, which is the one thing the panel exists to show.

### D5. Provenance is handed a measurement, not the means to compute one

The walk first reached `ProvenanceService` as a constructor dependency threaded through
`configureProvenance` and `provenanceIo`. Six hops to feed one call, and the service's own business
— owning the receipt — has nothing to do with how a document's text is found.

Chosen: `sourceFingerprinter(schemas, walk)` is bound once where the plugin's content model is
resolved, and the service takes the bound `fingerprintOf(collection, doc)`. It loses both the schema
map and the walk, and with them the three "is this collection translated here" lookups.

- *Rejected — one content reader for every consumer, selection included.* Selection sits in the two
  run paths, which hold the walk anyway because the pipeline writes through it; a reader would be a
  second way to say the same thing there.
- *Rejected — leave the pair in the service.* Every later consumer would carry it again, and the
  guarantee that the receipt and the panel measure one text would rest on three call sites passing
  the same value rather than on there being one value.

Costs: for a collection the plugin does not translate, `getStaleness` and `dismiss` now read the
receipt and the source document before finding nothing to measure, where they used to return early.
Both still answer the same thing, and the routes already refuse an unmanaged collection.

### D6. The two differential suites are frozen rather than deleted

`PayloadFields.differential.test.ts` and `PayloadLexical.differential.test.ts` compared the new
languages against the live old walker, so deleting the walker would have taken ~900 lines of
document-shape coverage with it.

Chosen: the old side's answers were recorded from it while it still existed, into
`__tests__/fixtures/{fields,lexical}.baseline.json`, and each suite now reads the baseline. A case
with no entry raises rather than passes, so a new case cannot quietly measure nothing.

- *Rejected — delete both suites with the walker.* The breadth of document shapes is the coverage;
  the live old side was only how it was obtained.
- *Rejected — keep the old walker alive for the tests.* That is the two-walker state this step
  exists to end.

## Risk notes

Classified **high**, and it is the highest of the three steps. It deletes the production
translation path and rewires provenance, so a wrong answer is lost or mis-recorded customer data,
not a missing translation.

- The loop described above is the failure this step exists to avoid, and it is silent once
  entered: the hash matches, so nothing reports it. AC3 is the guard, and it compares sets rather
  than samples.
- D9's one-time staleness is intended and must be distinguishable from the loop: AC4 says
  documents without embedded blocks do not move at all, AC5 says documents with them move once.
- The differential oracle has twice this week been found measuring the wrong thing. Any new
  comparison it gains must be shown to fail when the behaviour it checks is removed.
