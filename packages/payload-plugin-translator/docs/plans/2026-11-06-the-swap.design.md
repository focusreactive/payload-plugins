# The swap: one walk answers both questions

Issue #199 · design step **S** of [2026-10-18-the-rewiring.md](./2026-10-18-the-rewiring.md) §9

## Why

Two walkers coexist. The pipeline's own — `FieldChunkCollector` plus
`core/translation-pipeline/stages/text-expander/` — is the one in use. The traversal engine
(`core/traversal/`) with its two languages (`languages/`) is written, tested and wired to nothing:
nothing outside `languages/` imports `languages/`, and nothing outside those two folders and their
own tests imports `core/traversal`. This step retires the first.

The behavioural risk sits here — selection, write-back and fingerprint values — and the existing
differential tests (`languages/__tests__/*.differential.test.ts`) are its oracle: they already drive
the old collector and the new language over the same document and compare texts, addresses and the
resulting document.

### The hazard the epic carries, restated with its mechanism

One vocabulary of addresses holds three things together, and all three read it from one function,
`projectTranslatableContent`:

| What | How it gets the addresses |
|---|---|
| what may be translated at all | `everyTranslatableLeaf` in `selectLeaves.ts` |
| what counts as changed | `computeFieldFingerprints` hashes each entry by `idPath` |
| what the receipt records | `Provenance.service.record` iterates the fingerprint map's keys |

That function is field-level for rich text, by its own docblock: *"`richText` is field-level (one
entry, joined node text)"*. The recorder then does this:

```ts
const sent = new Map(leaves.map((leaf) => [String(leaf.idPath), leaf.answered]));
for (const [address, hash] of Object.entries(currentFields)) {
  hashes[address] = claimToRecord(sent.get(address), hash, alreadyClaimed[address]);
}
```

The loop runs over the fingerprint map; the lookup is string equality. Move the translation side to
addresses the fingerprint side does not produce and `sent.get("body")` is `undefined` for every
document, forever — not because of the data but because of the shape. `claimToRecord` then writes
`UNANSWERED`, which *"reads as changed, so the next run selects it again"*, and the loop closes:
mark stale, translate, fail to record, mark stale. No number of runs settles it.

The same reasoning applies to selection, which the epic does not name: `selectLeaves` builds
`everything` from the same function, so a run is handed `["body"]` while the new walk works in
`body.p1`. Three joints, one cause.

## Requirements

- R1 (in) One definition of what is translatable, read by both translation and staleness. Today
  `translatableLeaf.ts` promises exactly this (*"so the two can never disagree on the translatable
  set"*) and the promise is about to be broken by the new walk descending further than the
  projector does.
- R2 (in) Text inside a block embedded in rich text is translated. Today it never is:
  `collectSerializedLexicalTextNodes` descends only through `children`, and an embedded block
  carries its content under `fields`.
- R3 (in) A change to that text makes the translation stale. Today it cannot, for the same reason —
  so the text can rot in the target locale with nothing watching it.
- R4 (in) A host states which blocks may be translated inside rich text, through a published
  option. `PayloadFieldsConfig` already takes the two lists; nothing fills them.
- R5 (in) Rich text keeps today's granularity on the wire: one unit per container, carrying its own
  formatting. Container mode is the live default (`defaultExpanders = [new RichContainerExpander(),
  new PlainTextExpander()]`), not a flag; the Lexical language cuts per text node and must learn the
  other cut.
- R6 (in) The old walker and its expanders leave with this step. A second mechanism kept "just in
  case" is a second mechanism to maintain, and the swap is what #202 and #203 wait on.
- R7 (out) Finer receipt addresses. Deferred by the owner: a receipt address stays field-level, so
  one edited word re-sends the whole field. That is the real cost lever and it gets its own step.
- R8 (out) A partial translation reported as partial — R15 of the provider-port design. Unchanged
  here, and this step must not make it worse.
- R9 (out) A migration that rewrites existing receipts. Ruled out; see D8.

## Decision records

### D1. The receipt keeps field-level addresses; the walk folds onto them

A rich-text field stays one address (`body`), as it is today. The walk may produce as many targets
beneath it as it likes; everything found below the crossing is attributed to the address of the
leaf that crossed.

Rejected: move the receipt to per-unit addresses (`body.b1:cta.heading`). It is the finer and
eventually better shape, but it changes the address set of every stored receipt at once, forces a
decision about what an old receipt means, and buys nothing this step needs. R7 keeps it available.

**Consequence, which must be built and not assumed.** Three places learn the fold:

- the fingerprint map is keyed by the folded address;
- recording looks up a run's answer by the folded address — a field counts as answered when every
  target under it was answered, and a partially answered field records `UNANSWERED`, which is what
  `claimToRecord` already does for `answered === false`;
- a selection filter naming `body` matches every target whose folded address is `body`.

The fold point exists in the engine: in `walk.ts` a `LeafVisit` carries `idPath`, and at the moment
`boundary` returns a crossing that `idPath` *is* the field's address.

### D2. The text under a rich-text address includes what is embedded in it

`body`'s hash is taken over the text of its prose **and** the text of the blocks embedded in it that
the host allowed (D5). Anything else leaves R3 unmet: the new walk would translate text that
staleness cannot see.

### D3. One walk answers both questions

Fingerprints are computed by the same walk, with the same languages and the same block list, as the
translation. Not by a patched `collectSerializedLexicalTextNodes`.

Rejected: teach that helper to descend into `node.fields`. It lives in `core/kernel/lexical/` and
knows nothing of the host's block list, so it would hash text from blocks the host chose not to
translate — an edit there would mark the document stale although nothing about it is translatable.
Computing from the walk makes the list hold by construction, and restores R1 instead of adding a
second definition beside it.

### D4. An embedded block is not a language of its own

Its content is a Payload fields object with a Payload field schema — no structure vocabulary of its
own, and no data layout of its own. The contract says a language is what *"knows both its own
structure vocabulary and its own data layout"*; a block has neither separately, so a third language
would be a copy of `payload-fields`.

The round trip is already built: `Lexical.step` reads `node.fields` through `embedOf`,
`Lexical.boundary` hands the node back with `cursor.embed(kind, blockType, data)`, and
`PayloadFields.resolveEmbed` answers `{ languageId: PAYLOAD_FIELDS_ID, … }`. Arbitrary nesting comes
free: a block holding another rich text crosses into Lexical again.

What keeps the two independent is `richTextCrossing.ts`, which belongs to neither: a host that took
those names from one editor could serve only that editor, and an editor that took them from its host
could serve only that host. A separate "block language" is exactly the knot that file unties.

A new language is still the right answer for a genuinely different format — Slate, Markdown, TipTap.

### D5. The lever is the block list, not a depth limit

Depth is a poor proxy for cost: a block three levels down with a three-word heading costs three
words, while a flat rich text of ten thousand words costs ten thousand. Worse, cutting by depth
publishes a page in two languages at once, and silently — an `EmbedResolver` returning `null` skips
without a trace, which is right for "the host said no" and wrong for "we ran out of budget".

The lever is `PayloadFieldsConfig.blocks` / `inlineBlocks`, by block type, at any depth. A second,
finer lever already works and needs nothing: `custom.translateKit.exclude: true` on a field inside a
block, because such fields are ordinary Payload fields and `selects: isTranslatableLeaf` consults
`isFieldExcludedFromTranslation`.

### D6. The default is every block the host names at plugin level

~~**The default is every block the editor allows.**~~ Superseded 2026-11-06, after the blocks a
rich-text field's editor permits were found to be unreadable from this package at every point
available to it: before Payload sanitizes, the field's `editor` is an unresolved provider — which is
why `projectFieldLike` exists at all, "Field definitions embed Lexical editor configs containing
async functions" — and after sanitization the resolved definitions stay in closures
(`@payloadcms/richtext-lexical/dist/features/blocks/server/index.js:36-60`), never exposed as data.
The one remaining route, `getSubFields` per encountered node, is marked `@ts-expect-error - TODO: fix
this` in Payload's own source and was rejected as a surface to depend on.

**What the default is instead.** The host names the blocks once, at plugin level, and that list
applies to every field; a field may override it for itself. The principle the struck wording was
written to protect still holds and still decides: a default gives the right result, not the cheap
one, so the default translates everything the host listed rather than nothing until asked.

Rejected: empty until declared. Safe for the bill, and it leaves embedded text untranslated without
saying so — the defect R2 and R3 exist to remove — now once per rich-text field instead of once.

**The residual this leaves, which no mechanism can close.** A block added to a field's editor and
not to the plugin's list is silently untranslated. Nothing in this package can observe the
difference, so it belongs in the option's documentation beside D7's note that widening a
configuration is safe and narrowing it is not. The per-field override and the shape of the
declaration are designed in
[2026-11-06-the-crossing-surface.design.md](./2026-11-06-the-crossing-surface.design.md).

### D7. What a walk covers is configuration, not a run's choice

No per-run depth or block selection. With D3 the fingerprint is a function of what the walk covers,
so a run at one setting and a run at another produce different hashes for the same address and each
marks the other's work stale — a second way to build the loop this design is written to avoid.

Stated for the record, because it decides more than this step:

> Anything that changes **the set of translatable text** is configuration, and changing it costs a
> one-time staleness. Anything a run chooses may only narrow **which of the known addresses** to
> send — that is what the `stale` criterion does.

This also answers "developer or editor": an editor cannot reason about depth; they reason about
"this block type is translated", which is configuration.

One property to state rather than engineer around: widening the configuration is safe, narrowing it
is not. Text translated under a wider setting keeps its translation and loses its custodian. The
same is true of the block list and of any later lever; it belongs in the option's documentation.

### D8. No receipt migration; the fold reproduces today's join byte for byte

The idea was to rewrite still-fresh receipts in the new shape, so nothing reports stale. It does not
survive: the old engine never translated embedded block text, so that text is sitting in the target
locale in the source language. A migration would record "translated from this source" about text
that was never translated, and the stale mark is the only thing that would otherwise correct it. The
set of documents the migration could serve and the set it would lie about are the same set.

Instead, a constraint on the implementation, cheaper and checkable: **for a rich text with no
embedded block, the folded text must equal `leafSourceText`'s string exactly.** Both sides already
agree on the pieces — non-blank text nodes, depth-first through `children`, joined with `""` and
trimmed; `isEmpty` and `text.trim().length > 0` accept the same strings. Then a document without
embedded blocks does not go stale at all, honestly, and no migration has to exist.

### D9. The one-time staleness is accepted, and announced

What is left after D8 is exactly the documents that hold a text-bearing block inside rich text. For
them the mark is true: they contain text that has never been translated. It settles after one run
per document.

Cost, measured rather than assumed: the admin shows those locales out of date, and the next run on
such a document sends the whole field. Automatic translation on save is **not** triggered by it —
that gate is `hasSourceContentChanged`, which compares the document before and after a save through
`computeSourceFingerprint`, not the receipt.

What this buys instead of a mechanism: one sentence in the release note saying that documents with
blocks inside rich text will report out of date, and why. Without it an editor sees a mark on a
document nobody touched and concludes the plugin is broken.

### D10. `maxCrossings` stays a safety stop

Its docblock says what it is: *"Raise `maxCrossings` if the content is legitimately that deep"*. It
throws `TooManyCrossingsError` rather than truncating. Turning it into a cost budget would mean
translating a document halfway and reporting it as an exception.

### D11. The Lexical language gains container units; per-node stays behind them

R5. `textUnits` is where the cut is chosen, and the contract already anticipates both:
*"a rich text can offer one unit per text node, or the whole container as a single unit carrying its
own formatting"*. `collectInlineFragments` already exists and is what `RichContainerExpander` uses.

The fallback is kept as it is today: a tree whose containers are all skipped falls back to per-node,
because the two disagree on whitespace nodes and a fallback that translated something different
would not be one.

### D12. The differential harness is the oracle, and grows with this step

It already compares texts, addresses and the written document between `FieldChunkCollector` and
`payloadFieldsLanguage`. This step adds cases for container units, for embedded blocks, and the
byte-for-byte fingerprint equality of D8. Nothing in the swap is declared equivalent by reading.

### D13. A host declares the formats it may be holding as a list; each language owns its entry

`payloadFieldsLanguage` took one optional `RichTextCrossing` and decided the handoff itself: it
tested `field.type === "richText"`, then `isSerializedLexicalRoot(value)`, then cloned a
`SerializedLexicalRoot`. The language id was configurable, but the trigger and the data shape were
not — so the Payload language knew one editor, and a second format would be an edit to it rather
than an addition beside it.

Instead the host takes a list and asks each entry in turn:

```ts
export type ContentCrossing = (offer: {
  value: unknown;
  setValue: (next: unknown) => void;
  embed: EmbedResolver;
}) => Crossing | null;
```

Each language publishes its own entry next to itself — `lexicalContent()` beside `lexicalLanguage()`
— and the host's `boundary` becomes the loop, naming no format.

**The cut is by what each side knows.** Recognising `{ root }` and knowing that write-back is
in-place (so a working copy must be seated first) are the rich-text language's. Knowing that a field
is `localized` and not excluded is the host's. Which formats are in play, and in what order, is the
configuration's. Neither module may take the other's names — the rule `richTextCrossing.ts` already
states for itself: *"A host that took these names from one rich-text language could only ever be
configured with that language … a rich-text language that took them from its host could not serve a
second one."* Moving the whole test into the rich-text module would satisfy "each language owns its
crossing" and invert the coupling instead of removing it, because `field.type === "richText"` is the
host's word.

Three rules the list needs, all consequences rather than preferences:

- **First to answer wins**, and the order is the configuration's. Detecting two entries that accept
  one value would mean running every entry on every value; the cost is not worth a case a host
  creates by listing two readers of one format.
- **An entry that answers is the only gate.** It returns a crossing, and if the language then
  refuses the context that is `CannotEnterLanguageError`, not a fall-through to the next entry.
  Falling through would turn a misconfiguration into silence.
- **The host applies its own translatability rule before the list**, never an entry. The contract
  already requires it: *"a language that only translates part of its content must apply that rule
  here too — otherwise it crosses into content its host never marked."*

Rejected: keep the single optional crossing and add a second field later. The option is published by
this step, so its shape becomes a promise in a major — `richText: { languageId, blocks,
inlineBlocks }` says "exactly one rich-text format, exactly two kinds of embed", and widening it
afterwards is a breaking change in a release already out. A list of one costs almost nothing now.

What this buys today, before any second editor exists: the published option stops foreclosing one;
a field of some other type holding a foreign format becomes an entry rather than an impossibility,
where today `boundary` refuses it on its first line; and the seating of the working copy moves into
the module whose write-back makes it necessary, next to the reason for it.

The field-type test is dropped rather than moved. It was a cheap pre-filter, not a rule: an ordinary
text field holds a string, which no entry recognises. Where a host does not want a field handed over
at all, `isTranslatableLeaf` and `custom.translateKit.exclude` already say so.

Kept as a stated cost: `embed` is offered to every entry although embedding is a rich-text notion. A
format without embeds ignores the argument. The alternative — a per-format service bag — buys
nothing until a second format needs a different service.

## The three equalities, and the one deliberate inequality

What the oracle must show before the old walker is deleted:

| | Old | New | Must be |
|---|---|---|---|
| text sent for a rich text with no embedded block | container units | container units | equal |
| addresses of a run | field-level | field-level, folded | equal |
| the written document | — | — | equal |
| `body`'s fingerprint when a block **is** embedded | prose only | prose + allowed block text | **different, by design** |

The fourth row is D9's whole bill, and it is the only intended difference.

## Build sequence

Three commits, and the third is not divisible.

1. **The block list becomes an option and reaches the languages.** A published option carrying the
   blocks and inline blocks a host wants translated inside rich text, resolved into
   `PayloadFieldsConfig`. No behaviour change — nothing calls the languages yet. **D13 is built**:
   `ContentCrossing`, `lexicalContent()` and the host's loop are in the working tree, with the
   crossing list proved on a format and a field type neither language knows
   (`PayloadFields.contentCrossings.test.ts`). What is left of this step is the option that fills
   the lists from a host's config.
2. **Container units in the Lexical language**, with the per-node fallback of D11, and the
   differential cases for them. Still unwired, still no behaviour change.
3. **The swap.** Fingerprints computed from the walk and folded (D1–D3), the fold on recording, the
   pipeline moved onto the walk, and `FieldChunkCollector` plus `stages/text-expander/` deleted.

   **These cannot be split**, and the reason is not tidiness. Move fingerprints first and, until the
   translation side follows, a run still reports `body`, so recording finds it and writes the
   new with-blocks hash — claiming the embedded text is translated when it is not, and because the
   hash then matches, nothing will ever notice again. Move translation first and the permanent loop
   in §Why opens. Only together is either state avoided.

Then the documentation that is not code: the `DEPRECATIONS.md` entries this step owns, `@since` on
the new option, and the release-note sentence of D9 proposed to the owner for the README.

## Risk notes

- **Container parity is where the behaviour risk concentrates.** Marks, whitespace and the
  all-skipped fallback are the three places the old expander earned its complexity; the differential
  cases must cover each before anything is deleted.
- **The crossing seats a clone of the source into the working copy** (`seatSourceClone`), which is
  what makes it an overwrite rather than a re-translation of the previous translation. How that
  meets `DataReconciler`'s behaviour has to be walked, not assumed.
- **The two-document guarantees were demonstrated under the overwrite strategy only.** The epic left
  this to be settled or dissolved here. It is dissolved: the strategy port is gone from
  `core/domain/`, and what remains is refusal and compatibility — `enqueue-translation/model.ts`
  refuses the option, `AutoTranslate.wiring.ts` warns, and `legacyInput.ts` maps a stored
  `skip_existing` onto the `stale` criterion. There is no second strategy for the guarantee to be
  conditional on.

## Decisions by the owner

- 2026-11-06 — the receipt keeps field-level addresses; finer addresses are deferred to their own
  step.
- 2026-11-06 — fingerprints are computed by the same walk as the translation.
- 2026-11-06 — an embedded block is not a language of its own.
- 2026-11-06 — the lever is the block list, not a depth limit, and it is a developer's option, not
  an editor's.
- 2026-11-06 — the default is every block the editor allows.
- 2026-11-06 — no receipt migration, and no option gating the new behaviour; the one-time staleness
  is accepted and announced instead.
- 2026-11-06 — crossings into another language are a list the host iterates, and each language
  publishes its own entry; neither side names the other (D13).
- 2026-11-06 — D6's "every block the editor allows" is superseded: the editor's list is unreadable,
  so the default is every block the host names at plugin level, overridable per field.
- 2026-11-06 — the shipped rich-text language is renamed for its host: `payloadLexicalLanguage`,
  id `payload-lexical`, while the id is still internal and the rename costs nothing.
- 2026-11-08 — **the source value always replaces the target value in full.** A crossing hands the
  format the source locale's tree, and what the format produces is placed over the target locale's
  tree whole. Content an editor added by hand in the target locale is lost on the next translation.
  There are no exceptions and no per-case strategy: a rule with exceptions is the plugin guessing on
  the author's behalf, which is the defect this decision exists to prevent. Resolves the audit's F3.
- 2026-11-08 — **a change to content inside a block embedded in a rich text makes that rich text
  stale.** The embedded text is part of what the field's fingerprint covers, so editing only a
  block's heading must mark the field as needing translation.
- 2026-11-08 — **no mechanism is added for a translation orphaned by narrowing the block list.** When
  a block leaves the list its already-translated text stays in the document and stops being tracked.
  This is stated in the option's documentation and nothing is built to detect it.
- 2026-11-08 — **D6's mechanism is replaced.** D6 said the default is every block the host names at
  plugin level, "overridable per field"; the per-field override was removed on 2026-11-08 and the
  two sentences that still promise it (in D6, and in the owner decision of 2026-11-06 below it) are
  superseded. The default is every block declared in `payloadConfig.blocks`, widened by the additive
  `embeds` option and narrowed by nothing. Narrowing is expressed where it already was, with
  `exclude: true` on a field inside the block.
