# @focus-reactive/payload-plugin-visual-editing — Agent Guide

Payload v3 plugin: click-to-edit overlays on server-rendered draft content through Vercel stega markers and a `postMessage` bridge to the admin, plus an optional instant preview of text edits.

[`README.md`](./README.md) is the user document: when behaviour changes for a project that uses the plugin, update it, including "Upgrading". Read the rules below before changing anything.

## Things that are easy to break

- **Group edit targets by document, path, locale and anchor.** Three cards that each render `title` must not become one target around all three.
- **A `_meta` is a field reference.** `markRead` writes it on rich text, relationship and upload values and on populated documents, and an outer read leaves a value that has one as it is. Holders never leave `markRead`.
- **A holder path never crosses a relationship.** Do not look up the related collection's schema from the outer document.
- **The editable schema can refer to itself.** A referenced block nested in itself gives a cyclic schema. Walk it along a path or along data; never recurse over it and never serialise it. Only `src/shared/editableSchema/` builds and walks it; callers use `editableSchema.ts` (`isMarkable`, `holderFieldAt`, `richTextValueAt`, `schemaPathOfRichText`) and never read the object.
- **Add a field type to `editableSchema.ts` only together with its marker on the server.** The admin sends what that rule allows.
- **Server and admin must agree on leaves and shape.** Both import `isTextLeaf` and `shapeOf`. A change to either changes every node key.
- **The editor state leaves the admin only in `src/admin/instantPreview/unsavedStructures.ts`**, for a field the page announced with `ve:rich-text-rendered`, when the shape changes. Never per keystroke, never in a snapshot or a patch. The one other place is `RichTextEditReceiver`, which answers a `ve:rich-text-state-request` of the Live Preview window for a field of the open form, once per request and without the fields of blocks.
- **`readUnsavedRichText` trusts nothing in the request.** The document is read with the user's access, the state is validated and placed only into a field the editable schema lists as `richText`, block fields come from the saved document, and the `_meta` of the result comes from the read. The server never renders a posted state that did not go through it. The page may render in the browser the state the admin posted to it, with data the server already gave this page, and nothing else. A request without a state reads the saved value of the field under the same checks and a read key of that field alone, so no newer state and no read of another row of the same list replaces it; the page asks for the bases of several rows at once. Both read only the top-level field that holds the rich text unless `readWholeDocument` is set.
- **The field tracker releases a node before it reports it again.** `liveFields` keeps no node map: it releases a node by the address of the match it was given. A node reported with a new field before its old match was released would be patched as both fields.
- **A value is marked only when `hasMarker` says so, and the overlay never writes a value that stays the same.** `hasMarker` (`src/shared/stegaText.ts`) is the pattern of `@vercel/stega`. A range of zero-width code points also matches an em dash, curly quotes, an ellipsis and a narrow no-break space: the tracker wrote such an `aria-label` back unchanged, the observer reported the write and the page froze in that loop. The mutation pipeline skips an attribute record whose value equals its old value, so a write that changes nothing is never reported.
- **An adapter of a live rich text shows what `shownFor` returns and calls its `commit` once that is on screen, after every render.** The module waits for that commit before it starts the next render call; nothing else of its timing belongs in an adapter. The React adapter sets a render on the page with a plain `setState` and an answer of a call in `startTransition`, so the render on the page is never held behind a pending transition.
- **Where a structure is rendered is decided in `renderSources.ts` alone, the same for both adapters.** With a renderer of the value (`renderValue`, `renderRichTextValue`) and a grant from `payloadApi`, the check goes through the endpoint, not the call of the site (the action, `renderRichText`). The answer goes through the same renderer, so React updates the elements in place; without a grant the call of the site is made. A field without references renders on the page with a renderer of the value alone. Without `payloadApi` there is no base: a field with references waits for the call of the site. Without a renderer of the value nothing renders on the page. An adapter passes its renderers and never reads the grant, the source or the bases.
- **A grant is the only way a request without a session reads unsaved rich text.** `unsaved-rich-text` checks its signature and expiry, loads the user it names and reads only the document it names, with that user's access. It populates a relationship, upload or link node only when the saved value of the same field refers to the same document, and never a document of an auth or `payload-*` collection: `savedReferences.ts` holds every other id back in the `beforeRead` hook and `readAsUser` puts it back after the read, and a read that asked for the rule and did not get it answers nothing. `readUnsavedRichText` itself, which the site's own server code calls, populates what the posted state names. The admin posts a grant only to the origin of the Live Preview URL, once per page load and grant (`previewGrants.ts` remembers what it sent); a page that starts to listen asks for it with `ve:preview-grant-request`, because its announcements do not say whether it holds one.
- **The admin accepts a click from another origin only from the Live Preview window, on the origin of its URL** (`previewPages.ts`). The page never posts to `"*"`.
- **Never two render calls out.** A Server Action occupies the router's queue until it returns; `unsavedRender.ts` starts the next call only when the previous one has settled, whatever the component shows meanwhile. A render on the page is not a call.
- **A structure is shown by the render on the page first, and the server is called once per pause.** `unsavedRender.ts` calls `optimistic` synchronously in `tell` and shows what it returns before any call; the call waits `SERVER_CHECK_PAUSE_MS` after the last structure and replaces the render on the page only with an answer for the structure the editor holds. An answer of nothing keeps the render on the page. A field the page cannot render (no renderer, no base, a renderer that throws) keeps the `STRUCTURE_SETTLE_MS` path, so it gets no slower.
- **Only a structure with references needs a base.** `baseValues.ts` asks for the saved value of one field: when the editor types in a field that had references when the page loaded, or when a structure with references of such a field, or of any field after a save, needs it. A structure without references renders with no base, before and after a save, and asks nothing until the pause. Never ask for every field of the page at once. A base that did not arrive is asked for again; when one arrives, its watchers render the structure the editor holds on the page again.
- **A save makes the structure the editor holds the saved one, until the page renders again.** `ve:document-saved` names the document Payload reported as saved and the locale of the admin (`PreviewPageBridge.tsx`); a save of another document, such as one in a drawer, or in another locale changes nothing for the field, and a message without a document (an admin of 1.2.0) counts as a save of the field. On a save of its document, `liveRichText.ts` takes the render it showed for that structure (or the first one that arrives for it) as the saved render, so `shownFor`, the saved shape `unsavedRender.ts` and the overlay scope are told and the saved shapes the overlay keeps follow it. A saved render the adapter passes that differs from the one it passed before replaces it. Adapters keep passing the render the page loaded with; they never track saves themselves.
- **A base is forgotten on every save.** `baseValues.ts` drops the saved value and the answers of every field on `ve:document-saved` and ignores what arrives for a call that started before it. A stale base shows the old fields of a block until the server answers.
- **`liveRichTextOf` and `richTextAttributes` carry `hasReferences` and `meta`** for the render on the page; an identity without them (markup of an older version) keeps the server path.
- **The value built on the page equals the answer of `readUnsavedRichText`, markers, `_meta` and populated documents included.** `optimisticValue.ts` places, populates and marks the state with the functions the server uses from `src/shared/richText/`; change them on one side only and the node keys drift. `tests/realPayload/realPayloadOptimisticParity.int.spec.ts` judges it on a real Payload.
- **The fields of a block never leave the admin.** `unsavedStructures.ts` posts `withoutBlockFields(state)`.
- **`LiveRichText` never gets the value.** Its props are the field identity and a shape. Passing the value would serialise it into every draft page.
- **Every character of a marker's payload costs twelve bytes in the page.** `toStegaPayload` (`src/shared/shared.ts`) writes a field as a list without property names and the row ids of its key once, `toRichTextNodeMarker` writes a text node as `shape#address`. Only `fromStegaPayload` and `fromRichTextNodeMarker` read a payload; both still read the objects 1.2.0 wrote.
- **`#` separates the parts of a node key.** A rich text field whose key contains it is not marked and not answered.
- **`sessionOverlay.ts` starts an overlay again only when it has to**: when the session turns it on, or turns instant preview on or off. A change of mode, admin origin or locale reaches the running overlay through `sync` and its getters. Creating the overlay again on every render would drop the MutationObserver and the values the live fields hold; the React adapter starts it in an effect without dependencies and calls `sync` when the session changes.
- **Never decide whether a read is marked from state another read can touch.** A collection decides from the `args` its `afterOperation` receives. A global counts open reads per `req` object and marks only while no other read of it is open; it fails closed. A flag in `req.context` is shared with nested reads, with failed reads that never clear it, with concurrent reads and, through Payload's `createLocalReq`, with the `context` object of the caller, and each of these marked a published read. The rule lives in `markedReads.ts`; the hooks only report operations to it. It counts `operation === 'read'`, Payload's name for `findGlobal`, as a draft read, not a typo for `find`.
- **An edit on the page changes one field and nothing else.** For text, `textFieldTypeAt` (`editableSchema.ts`) decides it for the admin and for the endpoint alike: a field the schema lists as `text`, `textarea` or `email`; an upload and a rich text have their own rules below, behind the same checks. The endpoint checks the key against the draft read with the user's access, then builds the value to save from a read of the whole top-level field with `showHiddenFields`, so a row keeps the fields the user cannot read, and saves with `overrideAccess: false`. Both reads pass `context: { visualEditing: false }`: a marked read written back would save `_meta` objects. The first read must show text (a fallback of another locale counts), the second reads without a fallback so only the page's locale is written. The save passes `overrideLock: false`: the Local API otherwise overrides, and deletes, the lock of another editor. An edit names its locale on a project with locales, for the endpoint and for the form. The save passes `fallbackLocale: false`: a global otherwise fills the untouched siblings from the fallback locale and saves them into the page's locale. After the save the endpoint compares the value at the key before the save, in the result of the save and in what it sent: a value that stayed as it was although another one was sent is refused, because Payload drops a field whose `access.update` refuses the user without an error. It never compares the result with what it sent alone: a field hook that trims or reformats the value would make a save that succeeded look refused.
- **The tracker keeps a node the editor types into.** `beginEdit` holds the node while the page and the browser write into it; a render of the page with a marker is answered with the edited text (`shownText`) and the caret is put back (`onShownAgain`). `beginEdit` returns the element to make editable: the parent of the text node, not the holder, so the `<span>` and the icon inside a link survive a select-all. `endEdit` puts the node the page rendered back into that element, so React keeps writing into a node that is on the page. `showText` skips a node that is edited. Setting `data` to the value it has still queues a mutation record, so neither writes unchanged text.
- **A page next to the admin edits only what the form holds.** `inlineEditing.ts` asks `liveFields.holdsValueOf`: the admin sent a value for the field, so the form of its document is open. Anything else falls through to the click that opens the form. A page without an admin window sends every edit to the endpoint.
- **A replaceable upload is decided by `uploadCollectionAt` (`editableSchema.ts`) alone, for the admin and for both endpoints.** It names the collection of an `upload` field with one `relationTo`, without `hasMany` and without `filterOptions` that the editor can reach, and nothing for any other field. A draft save skips validation, so a field that filters what it takes is never written from the page. Payload strips `filterOptions` from the client config, so the schema of the admin cannot see it: `mediaPick.ts` refuses a field whose form state entry carries `filterOptions`, which Payload sets whenever the field declares one. The schema keeps the plain type name `"upload"` for such a field; the collection is kept beside the schema object (`schemaOfFields.ts`), as the localized names are, so nothing that compares or walks a schema changes. `field-edit` takes the id of a media document only after it converted it to the id type of that collection and read the document with the user's access; `media-options` lists with `overrideAccess: false`. Both go through `draftFieldOf` (`draftField.ts`), so a check added for one holds for the other.
- **The page only guesses which image can be replaced.** `imageReplacement.ts` offers the button for a target the page itself marked with `data-ve-path` (`tracker.isIdentifiedByThePage`: not an image the tracker identified by its `alt`, not a text holder it stamped), that is no live rich text (`data-ve-live-rich-text`), shows no tracked text and holds exactly one `<img>`. Whether the field is an upload is answered by the form (`ve:field-edit-refused`) or the endpoint (`422`); on either answer the page opens the field in the admin through the `openField` the badge hands the action, and never asks again by itself: Retry opens no drawer. Next to the admin the button is offered only for a document `liveFields.holdsFormOf` knows: the admin sent a value of one of its fields.
- **The button of a target lives in the badge layer, never in the page.** `editBadge.ts` draws it, `hoverController.ts` treats it as part of the badge, so the pointer moving from the image onto it keeps the target active. `client/overlay` knows an action only as a label and a function; what it does is passed in through `actionOf`.
- **The page shows a picked file by attributes only.** `shownImage.ts` sets `src`, removes `srcset` and `sizes` and rewrites the `srcset` of every `<source>`; it never removes an element React rendered and never writes `alt`, which the field tracker owns. `showMedia` returns what puts those attributes back; `imageReplacement.ts` calls it when the save of the pick fails and shows the file again when a retry saves it.
- **The admin opens the list drawer only for the Live Preview window, on its origin**, as `InlineEditReceiver` takes an edit, and posts `ve:media-picked` only there. The drawer is mounted per request and unmounted when it closes, so a second request opens a new one; while one is open every further request is refused. A drawer closed without a pick is told to the page with `ve:media-pick-cancelled`, so the page forgets the image it asked for; the page asks once per field while a pick is open.
- **One status path for text and images.** `editTransport.ts` holds every unsaved edit: `sendNow` delivers one edit without the waiting ones and reports each save of it to its sender, `holdInForm` counts a pick the admin wrote into the form as unsaved until `ve:document-saved` names its document. `inlineEditing.ts` flushes the transport on `pagehide` and when the page becomes hidden.
- **The picker hears keys on the document, in the capture phase, while it is open.** Focus falls to `<body>` when the focused control is disabled or hidden; Escape still closes, and any key takes the focus back to the first control of the dialog. After an upload the picker lists from the first page again, because the new file shifts the pages of the server.
- **Only `./rich-text` imports Lexical.** No other entry names `lexical`, `@lexical/*` or `src/client/inlineEditing/richText/`, not in an `import()` and not in an `import type`: a bundler resolves a dynamic import when it builds, so one such line would make every frontend install Lexical. The site hands the page a loader (`richTextEditor`), and `richTextEditing.ts` knows the editor only through the types of `richTextEditor.ts`. `src/rich-text` is covered by the page rule of the root `oxlint.config.ts`. The packages are optional peers and `devDependencies`, never `dependencies`, pinned to the version `@payloadcms/richtext-lexical` declares: the stored JSON is the format of that version.
- **The page never hands an element the site rendered to Lexical.** `richTextEditing.ts` hides the wrapper with an inline `display: none !important`, inserts a twin with the same tag and class after it and mounts the editor there; the admin's structure messages keep rendering the hidden wrapper. When the edit ends the twin is removed and the wrapper shown. A page of its own keeps a read-only clone of the twin (`data-ve-edited`) instead, until the wrapper's content changes while nothing of the field is unsaved (`editTransport.isUnsaved`), or the overlay is disposed; a click on it edits it again or, with the switch off, is passed on to the wrapper as a click. A wrapper the site replaced during the edit ends the edit and takes the twin with it. Every way a start can fail (the loader rejects, the editor throws, the state cannot be loaded) removes the twin, shows the wrapper and opens the field in the admin.
- **A click on editable rich text is taken at once and may wait.** With `richTextEditor` and inline editing on, `editInPlace` returns `true` for a wrapper `fieldOf` accepts, asks for the state if it does not hold it and starts the edit when the state and the editor are there; a refusal, a failed load or `RICH_TEXT_STATE_TIME_LIMIT_MS` without an answer calls the `openField` the edit targets hand it, which is the click handler of the target. Without `richTextEditor` it returns `false` and asks nothing.
- **The state the page holds is forgotten as soon as it may be stale.** It is kept per field, not per wrapper, so two wrappers of one field share it. `richTextEditing.ts` drops it when an edit of the field begins or ends and when the admin tells anything of its document (`ve:rich-text-structure`, `ve:field-patch`, `ve:field-snapshot`, `ve:document-saved`; a save without a document drops all), and asks again on the next pointer move over the wrapper, at most once per `RICH_TEXT_CHECK_PAUSE_MS` and wrapper.
- **A refused request for a state is `ve:rich-text-state-refused`, never `ve:field-edit-refused`.** The transport marks the posted edit of a field as failed on `ve:field-edit-refused`; a request that could not be answered must not touch an edit.
- **A node the page cannot edit is fixed: it can be left out, never changed, added or moved.** `editableNodes.ts` lists the edited types; every other node is wrapped as `ve-opaque` with its stored JSON before the state is loaded and unwrapped after it is exported, and nothing below it is walked. On the page `pageEditor.ts` removes one only by the deliberate action: a click, or Backspace/Delete beside it, selects it (a `NodeSelection`), and Backspace/Delete on that selection removes it in an update tagged for it. Delete, cut and insert commands over a range that spans one remove the text alone, a cut of a selected one does nothing, a copy that is not one of the loaded nodes is removed by a transform, and an update that changes the sequence without that tag or the tag of the history, or to something that is no part of the loaded sequence, is taken back. `$nodeBeside` answers for a caret on a text and on an element alike; without the element case Backspace at the start of the paragraph after a block fell through to Lexical and deleted text before the block. `editedStateOf` (`editedState.ts`) takes a state whose fixed nodes are a part of what the user was shown, in order (`storedNodesOf`): each posted node is matched to the next shown one that equals it without block fields, as serialised JSON (a key with the value `undefined`, which Payload's form holds on an upload node, equals a missing key), in a parent of the same type, and the stored node of that match is written when `type`, `id` and block identity match. Never restore block fields by `id` alone: an `inlineBlock` with the id of a `block` got that block's fields. `tests/realPayload/realPayloadRichTextEdit.int.spec.ts` judges the rule and `realPayloadRichTextOnThePage.int.spec.ts` compares the kept nodes byte for byte after an edit through a real Payload.
- **A removed node must be restorable for as long as the edit runs.** A page of its own never saves rich text while it is edited: `richTextEditing.ts` holds the latest state in the transport (`hold`), delivers it when the edit ends by a commit, ends the edit before the page is hidden or left (`commitBeforeThePageIsHidden`), and drops it on Escape (`drop`), so the draft holds the node until nothing can bring it back. Next to the admin the state is still posted while typing; `RichTextEditReceiver` keeps, per field and locale, the state it last answered (`createRunningEdits`) until `ve:rich-text-edit-ended`, which the page posts after the last state of a commit and of a cancel, or until the document or locale of the form changes. `richTextFormEditOf` then passes that state as what was shown and its fixed nodes as `remembered`: a posted state may hold any part of them, each written as the node the form holds now, or else as remembered, so block fields still never leave the admin. The page asks for no state of a field while it edits it, so an answer never replaces the state the edit began with.
- **The twin looks and measures like the wrapper.** `renderedLook.ts` builds the Lexical theme from the element the edit replaces (the wrapper, or the read-only twin): the class of the first element of each kind outside what the site rendered for a fixed node. A top-level fixed node shows a cleaned deep copy of the element at its index when the wrapper has as many child elements as the state has top-level nodes; the copy is `inert`, without `id` and `data-ve-*` attributes and without markers, so the field tracker and the edit targets never see it. Otherwise the labelled box stays.
- **The caret is resolved before the wrapper is swapped.** `richTextEditing.ts` turns the click into a count of editable text (`textPositionAtPoint` over the tracked text leaves of the wrapper, or the text of the read-only twin outside placeholders) at the click, also for a click that waits for the state, and `pageEditor.ts` places the caret at that count; a point taken after the swap is in another layout.
- **An edited rich text state is validated node by node, by one function for the endpoint and the form.** `editedStateOf` takes what the user was shown, what is stored and the formats of the field. It refuses forbidden keys, any key or value Lexical does not write for the node type, a node in a place Lexical does not allow, a `style` or node state the stored value does not hold, a format outside the field's (`richTextFormats.ts` reads the editor config on the server; the form can only answer the formats its state holds, because Payload strips `editor` from the client config), and a link whose `url` is not a string, is empty on a custom link, or is forbidden and not the address that same link `id` already stores. A new rule goes there, never into one caller. `field-edit` reads the field again after the save and compares with `isSameValue`, not with `JSON.stringify`: jsonb does not keep the order of keys. `RichTextEditReceiver` answers `withoutBlockFields(state)`: the fields of a block still never leave the admin.
- **The page keeps to the formats it was told.** `pageEditor.ts` registers transforms that turn a heading, quote or list the field does not allow into paragraphs, clear a text format or style it does not allow and unwrap a link, and blocks `FORMAT_TEXT_COMMAND` for such a format; the toolbar hides the buttons. A paste goes through the same transforms. Without them the server refuses the whole edit.
- **A link is `PageLinkNode`, not the node of `@lexical/link`** (Payload stores `fields` and `id`), and it splits as Lexical's link does: `insertNewAfter` inserts a copy with the same fields and a new id after itself. Payload's own `insertNewAfter` asks the parent block for a new block, which under Lexical 0.50 leaves three paragraphs and the text out of order.
- **The form shows an edited state only when `initialValue` is set with `value`.** Payload's Lexical field mounts its editor again when `initialValue` changes (`handleInitialValueChange` in its `Field.js`); an `UPDATE` with `value` alone changes the form and leaves the editor of the admin showing the old state.
- **A link address reaches the DOM only through `isAllowedLinkUrl`.** `PageLinkNode` sets `href` for an allowed address of a custom link and removes it otherwise, the toolbar refuses any other address, and nothing of the stored state is written with `innerHTML`: a placeholder shows its type through `textContent`.
- **One edit at a time.** `inlineEditing.ts` commits the rich text edit before a text edit begins, the text edit when a rich text edit begins (which may be after the click, once its state arrived), and both before the action of an image runs. `imageReplacement.ts` offers no button for a target inside rich text (`isInsideRichText`).
- **A keepalive request has a body limit.** `editTransport.ts` asks for `keepalive` only below `KEEPALIVE_BODY_LIMIT`; a browser rejects a longer one outright, and a rich text state is often longer.
- **`ve:open-field` with `focus: false` never opens a tab and never takes the focus.** The page posts it when an edit begins, so the form scrolls to the field while the caret stays on the page.

## Testing

- Specs mirror the source tree: `tests/server`, `tests/overlay`, `tests/admin`, `tests/instantPreview`, `tests/inlineEditing`, `tests/realPayload`, helpers in `tests/support`.
- Server behaviour is judged by the specs in `tests/realPayload/`, which read through a real Payload on in-memory sqlite and run in `node`, like `tests/server/latestReads.int.spec.ts` and `tests/server/unsavedRichTextWithoutSchemaCache.int.spec.ts`. `tests/realPayload/realPayloadRichTextLive.int.spec.ts` runs a real Payload under jsdom. A unit test that feeds `markRead` a hand-written document must use the shape those reads produce.
- Overlay tests post `MessageEvent`s on `window` and stub `window.parent` to stand in for the admin. Model both list shapes: the same Text node rendered again with another path (list keyed by row id) and with another key (list keyed by index).
- Add a failing test that reproduces the observed DOM or data before touching the overlay or the encoder.
- Lexical runs under jsdom for everything driven through `editor.update`. jsdom has no `Selection.modify` and no `getBoundingClientRect` on a `Range` or a `Text`: `tests/support/selectionRects.ts` stubs the rects, and a deletion or caret move by key is checked in a real browser, not in a spec. A command dispatched from outside an update commits in a microtask: wrap it in a discrete `editor.update` or await before asserting.

## Dev loop against an external consumer

A consumer that pins this package as a `file:` dependency copies `dist/` at install time. After a change:

```bash
bun run build
rsync -a --delete \
  packages/payload-plugin-visual-editing/dist/ \
  ../../<consumer>/node_modules/@focus-reactive/payload-plugin-visual-editing/dist/
```

Hard-refresh the preview tab or restart `next dev` if the client bundle does not change. In the preview, `document.querySelectorAll('[data-ve-target]')` lists every edit target; the attribute holds the marker path.

## Publishing

Public package, released by semantic-release through the monorepo flow. The peer range for `payload` and `@payloadcms/ui` is `^3.79.0`, because the bridge depends on `useConfig().getEntityConfig`; widen it only after testing against the lower bound. All peers are optional, because a site that uses only `./dom` needs none of them. The Lexical peers are optional as well: only `./rich-text` imports them, and only a site that passes `richTextEditor` imports that entry. `react` and `react-dom` are `^18.2.0 || ^19.0.0`: the page adapters use nothing newer than `useSyncExternalStore`, and the admin gets React 19 from Payload. `next` is not a peer because nothing imports it. Do not bump `version` by hand.
