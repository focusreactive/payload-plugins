# @focus-reactive/payload-plugin-visual-editing — Agent Guide

Payload v3 plugin: click-to-edit overlays on server-rendered draft content through Vercel stega markers and a `postMessage` bridge to the admin, plus an optional instant preview of text edits.

[`README.md`](./README.md) is the user document: when behaviour changes for a project that uses the plugin, update it, including "Upgrading". Read the rules below before changing anything.

## Things that are easy to break

- **Group edit targets by document, path, locale and anchor.** Three cards that each render `title` must not become one target around all three.
- **A `_meta` is a field reference.** `markRead` writes it on rich text, relationship and upload values and on populated documents, and an outer read leaves a value that has one as it is. Holders never leave `markRead`. With `instantPreview` the `_meta` of a value in an array row or a block carries the `key` of its field, built from the row ids as the key of a text field is (`keyOf` in `referenceField`); outside a row it carries none and the path is the key. A `hasMany` value names the field, never the entry: `placeOfField` drops the step of the entry together with its index, because a populated document has an `id` that would read as a row id. The page addresses an upload only by that key (`fieldKeyOfMarker`), so without it **Replace image** is never offered for an image in a row; `tests/realPayload/realPayloadUploadKeys.int.spec.ts` judges it against both endpoints.
- **A holder path never crosses a relationship.** Do not look up the related collection's schema from the outer document.
- **The editable schema can refer to itself.** A referenced block nested in itself gives a cyclic schema. Walk it along a path or along data; never recurse over it and never serialise it. Only `src/shared/editableSchema/` builds and walks it; callers use `editableSchema.ts` (`isMarkable`, `holderFieldAt`, `richTextValueAt`, `schemaPathOfRichText`) and never read the object.
- **Add a field type to `editableSchema.ts` only together with its marker on the server.** The admin sends what that rule allows.
- **Server and admin must agree on leaves and shape.** Both import `isTextLeaf` and `shapeOf`. A change to either changes every node key.
- **The editor state leaves the admin only in `src/admin/instantPreview/unsavedStructures.ts`**, for a field the page announced with `ve:rich-text-rendered`, when the shape changes. Never per keystroke, never in a snapshot or a patch. The one other place is `RichTextEditReceiver`, which answers a `ve:rich-text-state-request` of the Live Preview window for a field of the open form, once per request and without the fields of blocks.
- **`readUnsavedRichText` trusts nothing in the request.** The document is read with the user's access, the state is validated and placed only into a field the editable schema lists as `richText`, block fields come from the saved document, and the `_meta` of the result comes from the read. The server never renders a posted state that did not go through it. The page may render in the browser the state the admin posted to it, with data the server already gave this page, and nothing else. A request without a state reads the saved value of the field under the same checks and a read key of that field alone, so no newer state and no read of another row of the same list replaces it; the page asks for the bases of several rows at once. Both read only the top-level field that holds the rich text unless `readWholeDocument` is set.
- **The field tracker releases a node before it reports it again.** `liveFields` keeps no node map: it releases a node by the address of the match it was given. A node reported with a new field before its old match was released would be patched as both fields.
- **A value is marked only when `hasMarker` says so, and the overlay never writes a value that stays the same.** `hasMarker` (`src/shared/stegaText.ts`) is the pattern of `@vercel/stega`. A range of zero-width code points also matches an em dash, curly quotes, an ellipsis and a narrow no-break space: the tracker wrote such an `aria-label` back unchanged, the observer reported the write and the page froze in that loop. The mutation pipeline skips an attribute record whose value equals its old value, so a write that changes nothing is never reported.
- **An adapter of a live rich text shows what `shownFor` returns and calls its `commit` once that is on screen, after every render.** The module waits for that commit before it starts the next render call; nothing else of its timing belongs in an adapter. The React adapter sets a render on the page with a plain `setState` and an answer of a call in `startTransition`, so the render on the page is never held behind a pending transition.
- **Where a structure is rendered is decided in `renderSources.ts` alone, the same for both adapters.** With a renderer of the value (`renderValue`, `renderRichTextValue`) and a grant from `payloadApi`, the check goes through the endpoint, not the call of the site (the action, `renderRichText`). The answer goes through the same renderer, so React updates the elements in place; without a grant the call of the site is made. A field without references renders on the page with a renderer of the value alone. Without `payloadApi` there is no base: a field with references waits for the call of the site. Without a renderer of the value nothing renders on the page. An adapter passes its renderers and never reads the grant, the source or the bases.
- **A grant is the only way a request without a session reads unsaved rich text.** `unsaved-rich-text` checks its signature and expiry, loads the user it names and reads only the document it names, with that user's access. It populates a relationship, upload or link node only when the saved value of the same field refers to the same document, and never a document of an auth or `payload-*` collection: `savedReferences.ts` holds every other id back in the `beforeRead` hook and `readAsUser` puts it back after the read, and a read that asked for the rule and did not get it answers nothing. `readUnsavedRichText` itself, which the site's own server code calls, populates what the posted state names. The admin posts a grant only to the origin of the Live Preview URL, once per page load and grant (`previewGrants.ts` remembers what it sent); a page that starts to listen asks for it with `ve:preview-grant-request`, because its announcements do not say whether it holds one.
- **The admin accepts a click from another origin only from the Live Preview window, on the origin of its URL** (`previewPages.ts`). The page never posts to `"*"`.
- **Never two render calls out.** A Server Action occupies the router's queue until it returns; `unsavedRender.ts` starts the next call only when the previous one has settled, whatever the component shows meanwhile. A render on the page is not a call.
- **A structure is shown by the render on the page first, and the server is called once per pause.** `unsavedRender.ts` calls `optimistic` synchronously in `tell` and shows what it returns before any call; the call waits `SERVER_CHECK_PAUSE_MS` after the last structure and replaces the render on the page only with an answer for the structure the editor holds. An answer of nothing keeps the render on the page. A field the page cannot render (no renderer, no base, a renderer that throws) keeps the `STRUCTURE_SETTLE_MS` path, so it gets no slower.
- **Only a structure with references needs a base.** `baseValues.ts` asks for the saved value of one field: when the editor types in a field that had references when the page loaded, or when a structure with references of such a field, or of any field after a save, needs it. A structure without references renders with no base, before and after a save, and asks nothing until the pause. Never ask for every field of the page at once. A base that did not arrive is asked for again; when one arrives, its watchers render the structure the editor holds on the page again.
- **A save makes the structure the editor holds the saved one, until the page renders again.** `ve:document-saved` names the document Payload reported as saved and the locale of the admin (`PreviewPageBridge.tsx`); a save of another document, such as one in a drawer, or in another locale changes nothing for the field, and a message without a document (an admin of 1.2.0) counts as a save of the field. On a save of its document, `liveRichText.ts` takes the render it showed for that structure (or the first one that arrives for it) as the saved render, so `shownFor`, the saved shape `unsavedRender.ts` and the overlay scope are told and the saved shapes the overlay keeps follow it. A saved render the adapter passes that differs from the one it passed before replaces it. Adapters keep passing the render the page loaded with; they never track saves themselves.
- **A base is forgotten on every save.** `baseValues.ts` drops the saved value and the answers of every field on `ve:document-saved` and ignores what arrives for a call that started before it. A stale base shows the old fields of a block until the server answers.
- **`liveRichTextOf` and `richTextAttributes` carry `hasReferences` and `meta`** for the render on the page; an identity without them (markup of an older version) keeps the server path.
- **The value built on the page equals the answer of `readUnsavedRichText`, markers, `_meta` and populated documents included.** `optimisticValue.ts` places, populates and marks the state with the functions the server uses from `src/shared/richText/`; change them on one side only and the node keys drift. `tests/realPayload/realPayloadOptimisticParity.int.spec.ts` judges it on a real Payload.
- **The fields of a block never leave the admin.** `unsavedStructures.ts` posts `withoutBlockFields(state)`.
- **`LiveRichText` never gets the value.** Its props are the field identity and a shape. Passing the value would serialise it into every draft page.
- **Every character of a marker's payload costs twelve bytes in the page.** `toStegaPayload` (`src/shared/shared.ts`) writes a field as a list without property names and the row ids of its key once, `toRichTextNodeMarker` writes a text node as `shape#address`. Only `fromStegaPayload` and `fromRichTextNodeMarker` read a payload; both still read the objects 1.2.0 wrote.
- **Only the marker of a `textarea` says it holds several lines.** `markRead` asks `isMultiline` of the holder field and writes `multiline` into the identity; `toStegaPayload` writes it as a last `1` after the locale (`0` when there is none) and leaves it out for every other field, so a `text` marker costs nothing more. `textEditing.ts` edits a field without it as one line (`isOneLine`): Shift+Enter commits, a paste, the first typed text and any later `beforeinput` with a line break insert `oneLineOf` of it, and `insertLineBreak` and `insertParagraph` are prevented. `oneLineOf` and `editedTextOf` (`src/shared/fieldEdit.ts`) share one set of break characters, so the page shows what the server saves.
- **`#` separates the parts of a node key.** A rich text field whose key contains it is not marked and not answered.
- **`sessionOverlay.ts` starts an overlay again only when it has to**: when the session turns it on, or turns instant preview on or off. A change of mode, admin origin or locale reaches the running overlay through `sync` and its getters. Creating the overlay again on every render would drop the MutationObserver and the values the live fields hold; the React adapter starts it in an effect without dependencies and calls `sync` when the session changes.
- **Never decide whether a read is marked from state another read can touch.** A collection decides from the `args` its `afterOperation` receives. A global counts open reads per `req` object and marks only while no other read of it is open; it fails closed. A flag in `req.context` is shared with nested reads, with failed reads that never clear it, with concurrent reads and, through Payload's `createLocalReq`, with the `context` object of the caller, and each of these marked a published read. The rule lives in `markedReads.ts`; the hooks only report operations to it. It counts `operation === 'read'`, Payload's name for `findGlobal`, as a draft read, not a typo for `find`.
- **An edit on the page changes one field and nothing else.** For text, `textFieldTypeAt` (`editableSchema.ts`) decides it for the admin and for the endpoint alike: a field the schema lists as `text`, `textarea` or `email`; an upload and a rich text have their own rules below, behind the same checks. The endpoint checks the key against the draft read with the user's access, then builds the value to save from a read of the whole top-level field with `showHiddenFields`, so a row keeps the fields the user cannot read, and saves with `overrideAccess: false`. Both reads pass `context: { visualEditing: false }`: a marked read written back would save `_meta` objects. The first read must show text (a fallback of another locale counts), the second reads without a fallback so only the page's locale is written. The save passes `overrideLock: false`: the Local API otherwise overrides, and deletes, the lock of another editor. An edit names its locale on a project with locales, for the endpoint and for the form. The save passes `fallbackLocale: false`: a global otherwise fills the untouched siblings from the fallback locale and saves them into the page's locale. After the save the endpoint compares the value at the key before the save, in the result of the save and in what it sent: a value that stayed as it was although another one was sent is refused, because Payload drops a field whose `access.update` refuses the user without an error. It never compares the result with what it sent alone: a field hook that trims or reformats the value would make a save that succeeded look refused.
- **The tracker keeps a node the editor types into.** `beginEdit` holds the node while the page and the browser write into it; a render of the page with a marker is answered with the edited text (`shownText`) and the caret is put back (`onShownAgain`). `beginEdit` returns the element to make editable: the parent of the text node, not the holder, so the `<span>` and the icon inside a link survive a select-all. `endEdit` puts the node the page rendered back into that element, so React keeps writing into a node that is on the page. `showText` skips a node that is edited. Escape drops the value that still waits in the transport and sends the text the edit began with only when a value of this edit was delivered (`onDelivered` of `send`), so an edit that sent nothing saves nothing. Setting `data` to the value it has still queues a mutation record, so neither writes unchanged text.
- **A window the admin opened is next to the admin only once it was told of a form.** Payload's Preview button opens the draft page with `rel="opener"`, and the admin never talks to that tab; a page that posted its edits to `window.opener` there edited nothing. `findAdmin` in `inlineEditing.ts` answers the admin window for a framed page always, and for an opened one only while `liveFields.holdsAnyForm()`; the transport, the image replacement and the rich text editing take that function and never ask `findAdminWindow` where an edit goes. Listening for messages still uses `findAdminWindow`.
- **A target that is one line of text in a block is framed, hovered and clicked as that block.** `targetArea.ts` widens an inline target through parents it is the only content of, never into another field; the badge, the frames, the hover listeners and `findTargetAncestor` use it, the target itself and its attributes stay where they were. The frame of an edit is drawn by `editingFrame.ts` in a layer of its own: a CSS outline on an inline element that wraps is a polygon.
- **`plaintext-only` keeps white space, so the lines move.** Chrome lays out a `contenteditable="plaintext-only"` element with `white-space: pre-wrap`, and no inline `!important` value wins over it, so a text with two spaces in a row would wrap again the moment it is clicked. `textEditing.ts` begins the edit as `contenteditable="true"` and switches to `plaintext-only` on the first `keydown`, `paste`, `cut`, `drop`, `compositionstart` or `beforeinput` (`keepLinesUntilTheFirstChange`), before the browser acts on that event, so no formatting shortcut and no rich paste ever reaches the text. A switch made in `beforeinput` (text that arrives without a key: dictation, an emoji picker) leaves Chrome's caret before the inserted text when collapsed spaces precede it, so for `insertText` the edit prevents the event and inserts the text itself after the switch. Chrome also gives every `contenteditable` element `overflow-wrap: break-word` and `line-break: after-white-space`; `keepLineBreaking` writes the values the element had before the edit inline and takes them off when the edit ends, so a long word does not wrap on the click. Do not set `plaintext-only` at the click.
- **A click beside the text of a control is the page's.** `editInPlace` answers `CLICK_LEFT_TO_THE_PAGE` for a click in a link or button outside the element of the text, and `editTargets.ts` then neither prevents nor stops it.
- **A page next to the admin edits only what the form holds.** `inlineEditing.ts` asks `liveFields.holdsValueOf`: the admin sent a value for the field, so the form of its document is open. Anything else falls through to the click that opens the form. A page without an admin window sends every edit to the endpoint. The route of an edit is decided when it begins: `inlineEditing.ts` pins the admin window of the field (`pinAdmin`, for text in `editTextInPlace`, for rich text in `begin` of `richTextEditing.ts`), and the transport and `richTextEditing.ts` ask `adminOf` for every decision of that edit (pause, delivery, `send` or `hold`, the read-only twin, Escape, `ve:rich-text-edit-ended`). An edit begun through the endpoint stays there when the admin sends the values of a form while it runs; one begun in the form goes to the endpoint once that admin window is closed or replaced. A delivery to the admin forgets what the endpoint stored for the field (`savedEdits`), so a later save through the endpoint is not rebased on it. It remembers the value it gave the form instead (`givenToForm`, until the endpoint saves the field): the form may have saved it before its window closed, so a later save through the endpoint names it as `sentBefore`. That save, once it lands, also ends what the form was counted to hold of the field (`unsavedInForm`), because a closed admin never posts the `ve:document-saved` that would.
- **A replaceable upload is decided by `uploadCollectionAt` (`editableSchema.ts`) alone, for the admin and for both endpoints.** It names the collection of an `upload` field with one `relationTo`, without `hasMany` and without `filterOptions` that the editor can reach, and nothing for any other field. A draft save skips validation, so a field that filters what it takes is never written from the page. Payload strips `filterOptions` from the client config, so the schema of the admin cannot see it: `mediaPick.ts` refuses a field whose form state entry carries `filterOptions`, which Payload sets whenever the field declares one. The schema keeps the plain type name `"upload"` for such a field; the collection is kept beside the schema object (`schemaOfFields.ts`), as the localized names are, so nothing that compares or walks a schema changes. `field-edit` takes the id of a media document only after it converted it to the id type of that collection and read the document with the user's access; `media-options` lists with `overrideAccess: false`. Both go through `draftFieldOf` (`draftField.ts`), so a check added for one holds for the other.
- **The page only guesses which image can be replaced.** `imageReplacement.ts` offers the button for a target the page itself marked with `data-ve-path` (`tracker.isIdentifiedByThePage`: not an image the tracker identified by its `alt`, not a text holder it stamped), that is no live rich text (`data-ve-live-rich-text`), shows no tracked text and holds exactly one `<img>`. Whether the field is an upload is answered by the form (`ve:field-edit-refused`) or the endpoint (`reason: "not-editable"`, read by `readSaveRefusal` as for `field-edit`); on either answer the page opens the field in the admin through the `openField` the badge hands the action, shows no status and never asks again by itself: Retry opens no drawer. A pick the page chose itself (the pop-up window of Live Preview posts `mediaId`) is counted unsaved in the form when it is asked, and a refusal of it is a failure of the transport (`refuseAsked`) whose Retry asks the admin again for the same media, or the endpoint when no admin window is left. Next to the admin the button is offered only for a document `liveFields.holdsFormOf` knows: the admin sent a value of one of its fields.
- **The button of a target lives in the badge layer, never in the page.** `editBadge.ts` draws it, `hoverController.ts` treats it as part of the badge, so the pointer moving from the image onto it keeps the target active. It sits at the top left corner of the target, moved into the part of it that is in the window (`insetInView`) on every `reposition`, as the toolbar of rich text is, so an image taller than the window that is scrolled past its top still has a reachable button. `client/overlay` knows an action only as a label and a function; what it does is passed in through `actionOf`.
- **A rectangle the browser measured is in the space of the window, not of the layer it is drawn in.** With CSS `zoom` on `<body>` or above it (`body { zoom: 1.25 }`), `getBoundingClientRect`, `innerWidth` and the pointer report the zoomed page, and a layer appended to `<body>` is zoomed once more. `placeFrame` (frames, the badge, the frame of an edit), the button of the badge, the toolbar of rich text and the toggle divide what they write by `zoomOf` (`src/client/overlay/zoom.ts`, `currentCSSZoom`, 1 where the browser does not tell it) of the element they place, and compare with the window in the space of the window. A new element placed from a measured rectangle goes through `rectInZoomOf` or `zoomOf`; place it after it is in the page, since an element that is not rendered has no zoom.
- **The page shows a picked file by attributes only.** `shownImage.ts` sets `src`, removes `srcset` and `sizes` and rewrites the `srcset` of every `<source>`; it never removes an element React rendered and never writes `alt`, which the field tracker owns. `showMedia` returns what puts those attributes back; `imageReplacement.ts` calls it when the save of the pick fails and shows the file again when a retry saves it.
- **The admin opens the list drawer only for the Live Preview window, on its origin**, as `InlineEditReceiver` takes an edit, and posts `ve:media-picked` only there. The drawer is mounted per request and unmounted when it closes, so a second request opens a new one; while one is open every further request is refused. A drawer closed without a pick is told to the page with `ve:media-pick-cancelled`, so the page forgets the image it asked for, and so is a drawer still open when `MediaPickReceiver` unmounts (the admin went to another document). The page asks once per field while a pick is open: `imageReplacement.ts` asks again for a field whose request went to another admin window, to one that is closed, or is older than `MEDIA_PICK_TIME_LIMIT_MS`, because nothing else would ever free that field.
- **One status path for text and images.** `editTransport.ts` holds every unsaved edit: `sendNow` delivers one edit without the waiting ones and reports each save of it to its sender, `holdInForm` counts a pick the admin wrote into the form as unsaved until `ve:document-saved` names its document. `inlineEditing.ts` flushes the transport with `flushBeforeLeaving` on `pagehide` and when the page becomes hidden: every save that waits for an earlier one starts at once, because the page may be gone before the earlier one answers; otherwise saves go one after the other. Two saves of one field never race: a queued save is skipped when a newer one of its field was queued before its turn (`latestQueued`), a save that starts while an earlier one of its field is on the way names that one's value as `sentBefore`, which the endpoint accepts as well as `base`, so either may land first, and only the answer of the latest posted save of a field changes its status (`latestPosted`). A save says `saved` only when nothing waits, nothing is on the way and the form holds no edit of the page. Every status goes through `report`, which says `failed` for as long as the transport holds a failed edit, with the refusal of the latest one: an edit of another field never hides a failure. Only a save of that edit (`retry`) or a newer edit of the same field (`supersede` in `send`, `hold` and `sendNow`, a pick in `holdInForm`) removes it. `imageReplacement.ts` writes no status of its own: every failure, also a refused pick, is held by the transport with what its Retry does. `field-edit` answers a `reason` next to `saved: false` (`refusalOfStatus` in `draftField.ts`, `SAVE_REFUSALS` in `src/shared/fieldEdit.ts`, `changed` included); the form refuses without one, so next to the admin the status says **Not saved**. `settle` does nothing while the form holds no edit of the page, so a save in the admin never brings a status back.
- **The picker hears keys on the document, in the capture phase, while it is open.** Focus falls to `<body>` when the focused control is disabled or hidden; Escape still closes, and any key takes the focus back to the first control of the dialog. After an upload the picker lists from the first page again, because the new file shifts the pages of the server. A list that is drawn again keeps the focus on the document that had it; **Load more** puts it on the first document it added and an upload on the uploaded one, because the control that had it is hidden or disabled by then. The dialog has a fixed height and the grid takes what is left, so a search without a result moves nothing.
- **Only `./rich-text` imports Lexical.** No other entry names `lexical`, `@lexical/*` or `src/client/inlineEditing/richText/`, not in an `import()` and not in an `import type`: a bundler resolves a dynamic import when it builds, so one such line would make every frontend install Lexical. The site hands the page a loader (`richTextEditor`), and `richTextEditing.ts` knows the editor only through the types of `richTextEditor.ts`. The seam between them is not published: `./rich-text` exports one opaque `richTextEditor` (`RichTextEditorHandle`, made by `handleOf`), the loader option is typed `() => Promise<RichTextEditorModule>`, and `editorOf` checks the loaded module before the page uses it, so `EditSessionOptions`, `EditSession` and the types they name can change without a breaking release. `src/rich-text` is covered by the page rule of the root `oxlint.config.ts`. The packages are optional peers and `devDependencies`, never `dependencies`, pinned to the version `@payloadcms/richtext-lexical` declares: the stored JSON is the format of that version.
- **The page never hands an element the site rendered to Lexical.** `richTextEditing.ts` hides the wrapper with an inline `display: none !important`, inserts a twin with the same tag and class after it and mounts the editor there; the admin's structure messages keep rendering the hidden wrapper. When the edit ends the twin is removed and the wrapper shown. A page of its own keeps a read-only clone of the twin (`data-ve-edited`) instead, until the wrapper's content changes while nothing of the field is unsaved (`editTransport.isUnsaved`), or the overlay is disposed; a click on it edits it again or, with the switch off, is passed on to the wrapper as a click. A wrapper the site replaced during the edit ends the edit and takes the twin with it. Every way a start can fail (the loader rejects, the editor throws, the state cannot be loaded) removes the twin, shows the wrapper and opens the field in the admin. An error of Lexical after the start commits the edit: the latest state is kept, the state the edit began with is never sent back.
- **A click on editable rich text is taken at once and may wait.** With `richTextEditor` and inline editing on, `editInPlace` returns `true` for a wrapper `fieldOf` accepts, asks for the state if it does not hold it and starts the edit when the state and the editor are there; a refusal, a failed load or `RICH_TEXT_STATE_TIME_LIMIT_MS` without an answer calls the `openField` the edit targets hand it, which is the click handler of the target. Without `richTextEditor` it returns `false` and asks nothing.
- **The state the page holds is forgotten as soon as it may be stale.** It is kept per field, not per wrapper, so two wrappers of one field share it. `richTextEditing.ts` drops it when an edit of the field begins or ends and when the admin tells anything of its document (`ve:rich-text-structure`, `ve:field-patch`, `ve:field-snapshot`, `ve:document-saved`; a save without a document drops all), and asks again on the next pointer move over the wrapper, at most once per `RICH_TEXT_CHECK_PAUSE_MS` and wrapper. A page of its own hears no such news, so a click begins an edit from a held state only within `RICH_TEXT_STATE_FRESH_MS` of its answer and asks again otherwise.
- **A save through the endpoint names what its edit began from, and the endpoint saves nothing over a newer value.** Text and rich text edits carry `base` (`textEditing.ts` the text it began with, `richTextEditing.ts` the state it was given); `fieldEditEndpoint.ts` compares it, without markers, with the field in the read as the editor sees it and in the read as it is stored, and answers `412` and `changed` when neither holds it. A saved edit with a `base` is answered with the `value` the field holds after the save, read with the user's access. `editTransport.ts` keeps per field what the last save started from, sent and stored (`savedEdits`): a later save whose `base` is either of the first two is sent with the stored value as its `base`, so a field hook that trims, or Lexical's own normalisation, never looks like a change elsewhere. A field refused as `changed` stays failed: `supersede` keeps that failure, and the transport sends nothing more of the field until `retry` (`saveStatus.ts` offers **Reload** for it, not **Retry**). The admin path never sees `base`: `messageOf` strips it, and the form has no stale value to guard.
- **A page of its own adds one version per edit of a document whose drafts do not autosave.** Payload adds a version for every draft save of such a collection or global, and `autosave: true` on the Local API does not change it: `updateLatestVersion` only updates a version that has an `autosave` column set, and that column exists only when `versions.drafts.autosave` is on. So `field-edit` answers `autosave` next to `saved: true`, and once a save of a document answered `false` `editTransport.ts` (`savedWhenEditsEnd`) gives `send` no pause timer for that document: the value waits until the edit ends (`flush`), the page is hidden or left, or the overlay is disposed. `tests/realPayload/realPayloadEditVersions.int.spec.ts` counts the versions.
- **A refused request for a state is `ve:rich-text-state-refused`, never `ve:field-edit-refused`.** The transport marks the posted edit of a field as failed on `ve:field-edit-refused`; a request that could not be answered must not touch an edit. The refusal carries a `reason` (`InlineEditReceiver`, `RichTextEditReceiver` and `MediaPickReceiver` send `not-editable`, a pick while the drawer is open or of media the admin could not read `failed`), and the page reads it with `readSaveRefusal`, as the answer of `field-edit`, so one cause shows one status on both routes; a message without a reason is `failed`.
- **A node the page cannot edit is fixed: it can be left out, never changed, added or moved.** `editableNodes.ts` lists the edited types; every other node is wrapped as `ve-opaque` with its stored JSON before the state is loaded and unwrapped after it is exported, and nothing below it is walked. On the page `pageEditor.ts` removes one only by the deliberate action: a click, or Backspace/Delete beside it, selects it (a `NodeSelection`), and Backspace/Delete on that selection removes it in an update tagged for it. Delete, cut and insert commands over a range that spans one remove the text alone, a cut of a selected one does nothing, a copy that is not one of the loaded nodes is removed by a transform, and an update that changes the sequence without that tag or the tag of the history, or to something that is no part of the loaded sequence, is taken back. `$nodeBeside` answers for a caret on a text and on an element alike; without the element case Backspace at the start of the paragraph after a block fell through to Lexical and deleted text before the block. `editedStateOf` (`editedState.ts`) takes a state whose fixed nodes are a part of what the user was shown, in order (`storedNodesOf`): each posted node is matched to the next shown one that equals it without block fields, as serialised JSON (a key with the value `undefined`, which Payload's form holds on an upload node, equals a missing key), in a parent of the same type, and the stored node of that match is written when `type`, `id` and block identity match. Never restore block fields by `id` alone: an `inlineBlock` with the id of a `block` got that block's fields. `tests/realPayload/realPayloadRichTextEdit.int.spec.ts` judges the rule and `realPayloadRichTextOnThePage.int.spec.ts` compares the kept nodes byte for byte after an edit through a real Payload.
- **A removed node must be restorable for as long as the edit runs.** A page of its own saves rich text on each pause (`send`) only while the state holds every fixed node the edit began with; once one is removed `richTextEditing.ts` holds the latest state in the transport (`hold`), delivers it when the edit ends by a commit, ends the edit before the page is hidden or left (`commitBeforeThePageIsHidden`), and drops it on Escape (`drop`), sending the state the edit began with when one of this edit was delivered, so the draft holds the node until nothing can bring it back. The read-only twin is kept only when the wrapper did not render again after the last save (`showsWhatWasSaved`). Next to the admin the state is still posted while typing; `RichTextEditReceiver` keeps, per field and locale, the state it last answered (`createRunningEdits`) until `ve:rich-text-edit-ended`, which the page posts after the last state of a commit and of a cancel, or until the document or locale of the form changes. `richTextFormEditOf` then passes that state as what was shown and its fixed nodes as `remembered`: a posted state may hold any part of them, each written as the node the form holds now, or else as remembered, so block fields still never leave the admin. The page asks for no state of a field while it edits it, so an answer never replaces the state the edit began with.
- **The twin copies the chain of elements down to the one that holds the rendered nodes.** A site often renders `div[data-ve-path] > div.prose > nodes` (`apps/cms` does). `chainOf` (`richTextTwin.ts`) walks from the identity element through elements with exactly one element child and no text of their own, and stops before a rendered node (a `p`, heading, list, quote, or an element with text), before an empty element, and at once when the state holds one fixed node alone. `twinOf` copies tag and class of each element of the chain and returns the outermost copy (`root`, what is inserted, hidden, kept read-only and removed) and the innermost (`content`, where Lexical mounts and which carries the editor attributes); `contentOf` names the same element of what the edit replaces, for the theme and the copies of fixed nodes. `readOnlyCopyOf` takes the editor attributes off the innermost element and removes Lexical's block cursor and decorator boundary, which would otherwise count as children when the copy is edited again.
- **The twin looks and measures like the wrapper.** `renderedLook.ts` builds the Lexical theme from the element the edit replaces (the wrapper, or the read-only twin): the class of the first element of each kind outside what the site rendered for a fixed node. A top-level fixed node shows a cleaned deep copy of the element at its index when the wrapper has as many child elements as the state has top-level nodes; the copy is `inert`, without `id` and `data-ve-*` attributes and without markers, so the field tracker and the edit targets never see it. Otherwise the labelled box stays.
- **Lexical shows italic only by a class when the text is bold as well.** Its text element is `<strong>` for bold, `<em>` only for italic alone; `renderedLook.ts` always gives `text.italic` the class `ve-rich-text-italic`. The icon a site puts first in a list item cannot be an element in Lexical's DOM, so `renderedLook.ts` draws it as `li::before` from the computed style of the first one, in a style element `editSession.ts` keeps for the read-only twin too.
- **Lexical lays out its root with `white-space: pre-wrap` and `word-break: break-word`.** A stored text with two spaces in a row, which the site collapses, wrapped differently in the twin. `renderedLook.ts` reads from the first element the site rendered whether it collapses white space and its `word-break`, `overflow-wrap` and `line-break`; `pageEditor.ts` writes those three inline on the twin after `setRootElement` and, when the site collapses, drops the spaces the browser would not show (`$collapseSpaces`, the rule of CSS per block: runs, the start and end of a line, around a line break; code text untouched) in an update tagged `HISTORY_MERGE_TAG` before the baseline of `reportChange`, so it is no change and no undo step. The caret count of the click is in the stored text: `shownOffsetOf` maps it to the shown one. The collapsed text is what the first real change saves. Lexical also adds a `<br data-lexical-managed-linebreak>` after a line break that ends a block, so the empty last line has a height; a browser shows no line for a trailing `<br>`, so a list item that ends in one doubled its height in the twin. `ADDED_LINE_STYLE` (`richTextTwin.ts`) hides that added `<br>` when it follows a `<br>` of the state, in the twin and in the read-only copy, except in the block `pageEditor.ts` marks with `data-ve-caret-on-added-line` while a collapsed caret sits after that ending break, so the line the editor types on is shown.
- **The twin takes its direction from the site, not from the state.** Lexical writes `dir` from the stored `direction` on every element node and `dir="auto"` on a new top-level block; the attribute brings `unicode-bidi: isolate` and a direction the site does not have, so the words of a left-to-right state reorder on a right-to-left page. `pageEditor.ts` (`keepDirectionOfTheSite`) takes every `dir` off the elements of the editor after `setRootElement` and after each update, puts back the `dir` of the twin itself, which `twinOf` copies from the chain of the site, and leaves the copies of fixed nodes alone. Only the DOM changes: the `direction` of the state is saved as Lexical holds it, as the admin saves it.
- **The toolbar is shown for the whole edit, above the edited element**, not above the selection; `pageEditor.ts` turns a paragraph that begins with a markdown prefix into the block, only for formats of the field.
- **In the pop-up window of Live Preview the list of media opens on the page.** The page posts `ve:pick-media` with `mediaId`; `MediaPickReceiver` runs the checks of a pick, reads the document with the editor's access and writes it without a drawer, or refuses.
- **The caret is resolved before the wrapper is swapped.** `richTextEditing.ts` turns the click into a count of editable text (`textPositionAtPoint` over the tracked text leaves of the wrapper, or the text of the read-only twin outside placeholders) at the click, also for a click that waits for the state, and `pageEditor.ts` places the caret at that count; a point taken after the swap is in another layout.
- **An edited rich text state is validated node by node, by one function for the endpoint and the form.** `editedStateOf` takes what the user was shown, what is stored and the formats of the field. It refuses forbidden keys, any key or value Lexical does not write for the node type, a node in a place Lexical does not allow, a `style` or node state the stored value does not hold, a format outside the field's, and a link whose `url` is not a string, is empty on a custom link, or is forbidden and not the address that same link `id` already stores. A new rule goes there, never into one caller. `field-edit` reads the field again after the save and compares with `isSameValue`, not with `JSON.stringify`: jsonb does not keep the order of keys. `RichTextEditReceiver` answers `withoutBlockFields(state)`: the fields of a block still never leave the admin.
- **The formats of a field are the formats its editor config allows plus those its value holds, on every path.** `richTextFormats.ts` reads the config on the server, and both endpoints add the value. Payload strips `editor` from the client config, so `RichTextEditReceiver` asks `rich-text-value` for the formats when the page asks for the state (in the message handler, never in an effect), adds what the form holds and keeps them with the state the edit began with; when that request fails it falls back to the formats the form holds.
- **The admin writes into the form only a field the user may update.** `updatableFormFieldOf` (`formEdit.ts`) checks `docPermissions` of `useDocumentInfo` along the steps of the key (`fieldPermissions.ts`: groups and array rows through `fields`, blocks through `blocks`), for text, media picks and rich text alike, and refuses with `ve:field-edit-refused` or `ve:rich-text-state-refused`. Payload drops such a field on save without an error, so without it the page would show a save that never lands.
- **An endpoint the session cookie opens reads only a body sent as `application/json`** (`jsonBodyOf` in `endpointJson.ts`): `preview-grant`, `field-edit`, `media-options`, `rich-text-value`. A page of another site can post `text/plain` or a form without a CORS preflight. `unsaved-rich-text` keeps `bodyOf`: the page posts it as `text/plain` on purpose, and a grant, not a cookie, opens it. Every read and save of these endpoints runs inside their `try`, so a thrown error is answered with a reason and the CORS headers.
- **The page keeps to the formats it was told.** `pageEditor.ts` registers transforms that turn a heading, quote or list the field does not allow into paragraphs, clear a text format or style it does not allow and unwrap a link, and blocks `FORMAT_TEXT_COMMAND` for such a format; the toolbar hides the buttons. A paste goes through the same transforms. Without them the server refuses the whole edit.
- **A link is `PageLinkNode`, not the node of `@lexical/link`** (Payload stores `fields` and `id`), and it splits as Lexical's link does: `insertNewAfter` inserts a copy with the same fields and a new id after itself. Payload's own `insertNewAfter` asks the parent block for a new block, which under Lexical 0.50 leaves three paragraphs and the text out of order.
- **The form shows an edited state only when `initialValue` is set with `value`.** Payload's Lexical field mounts its editor again when `initialValue` changes (`handleInitialValueChange` in its `Field.js`); an `UPDATE` with `value` alone changes the form and leaves the editor of the admin showing the old state.
- **A link address reaches the DOM only through `isAllowedLinkUrl`.** `PageLinkNode` sets `href` for an allowed address of a custom link and removes it otherwise, the toolbar refuses any other address, and nothing of the stored state is written with `innerHTML`: a placeholder shows its type through `textContent`.
- **One edit at a time.** `inlineEditing.ts` commits the rich text edit before a text edit begins, the text edit when a rich text edit begins (which may be after the click, once its state arrived), and both before the action of an image runs. `imageReplacement.ts` offers no button for a target inside rich text (`isInsideRichText`).
- **A keepalive request has a body limit.** `editTransport.ts` asks for `keepalive` only below `KEEPALIVE_BODY_LIMIT` UTF-8 bytes of the body, not characters; a browser rejects a longer one outright, and a rich text state is often longer.
- **An edit on the page leaves the form of the admin where it is.** The page posts no `ve:open-field` when a text or rich text edit begins: in Live Preview the frame of the page sticks inside the scrolling admin, so a form scrolled to the field moved the frame under the pointer and the next click landed on another field. `ve:open-field` is posted only by a click that opens the field in the admin. The admin still takes `focus: false` (expand and show the field, no tab, no focus) from a page of an earlier version.

## Testing

- Specs mirror the source tree: `tests/server`, `tests/overlay`, `tests/admin`, `tests/instantPreview`, `tests/inlineEditing`, `tests/realPayload`, helpers in `tests/support`.
- Server behaviour is judged by the specs in `tests/realPayload/`, which read through a real Payload on in-memory sqlite and run in `node`, like `tests/server/latestReads.int.spec.ts` and `tests/server/unsavedRichTextWithoutSchemaCache.int.spec.ts`. `tests/realPayload/realPayloadRichTextLive.int.spec.ts` runs a real Payload under jsdom. A unit test that feeds `markRead` a hand-written document must use the shape those reads produce.
- Overlay tests post `MessageEvent`s on `window` and stub `window.parent` to stand in for the admin. Model both list shapes: the same Text node rendered again with another path (list keyed by row id) and with another key (list keyed by index).
- Add a failing test that reproduces the observed DOM or data before touching the overlay or the encoder.
- Lexical runs under jsdom for everything driven through `editor.update`. jsdom has no `Selection.modify` and no `getBoundingClientRect` on a `Range` or a `Text`: `tests/support/selectionRects.ts` stubs the rects, and a deletion or caret move by key is checked in a real browser, not in a spec. A command dispatched from outside an update commits in a microtask: wrap it in a discrete `editor.update` or await before asserting.

## Dev loop against an external consumer

A consumer that pins this package as a `file:` dependency copies `dist/` at install time. After a change:

```bash
bun run build
rsync -a --delete \
  packages/payload-plugin-visual-editing/dist/ \
  ../../<consumer>/node_modules/@focus-reactive/payload-plugin-visual-editing/dist/
```

Hard-refresh the preview tab or restart `next dev` if the client bundle does not change. In the preview, `document.querySelectorAll('[data-ve-target]')` lists every edit target; the attribute holds the marker path.

## Publishing

Public package, released by semantic-release through the monorepo flow. The peer range for `payload` and `@payloadcms/ui` is `^3.79.0`, because the bridge depends on `useConfig().getEntityConfig`; widen it only after testing against the lower bound. All peers are optional, because a site that uses only `./dom` needs none of them. The Lexical peers are optional as well: only `./rich-text` imports them, and only a site that passes `richTextEditor` imports that entry. `react` and `react-dom` are `^18.2.0 || ^19.0.0`: the page adapters use nothing newer than `useSyncExternalStore`, and the admin gets React 19 from Payload. `next` is not a peer because nothing imports it. Do not bump `version` by hand.
